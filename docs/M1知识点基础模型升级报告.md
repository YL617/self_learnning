## 3. 数据库变化

### 3.1 `knowledge_points` 追加 5 列

全部 **nullable、无 server_default** → 存量数据零回填，加列在两边都是纯 `ALTER TABLE ADD COLUMN`。

| 列 | 类型 | 可空 | 默认 | 语义 | 少了会怎样 |
|---|---|---|---|---|---|
| `code` | `VARCHAR(64)` | ✅ | — | 稳定编码（如 `DS.TREE.BST`） | 改名/换学科就断链，导入也无法对账 |
| `aliases` | `JSON` | ✅ | — | 别名数组（如 `["堆栈","stack"]`） | ⚠️ `栈`/`堆栈`/`stack` 会被建成 3 条知识点 → **同一个知识点的掌握度被拆成 3 份，学生永远达不到掌握** |
| `difficulty` | `VARCHAR(16)` | ✅ | — | `easy` / `medium` / `hard` | 推荐只能按掌握度盲排。**注意：它绝不参与掌握度计算** |
| `estimated_minutes` | `INTEGER` | ✅ | — | 预估学习时长（分钟） | 今日建议给不出一句「要多久」 |
| `import_batch_id` | `INTEGER` | ✅ | — | 所属导入批次 | 「失败回滚」无法实现 |

**为什么 `aliases` 用原生 JSON 类型而不是 JSON 文本**：用 `Text` 存 JSON 时，`knowledge_point.aliases` 在业务代码里就是一个**可以逐字符迭代的字符串** —— 一个必然会踩的坑。原生 JSON 让该属性天然是 `list[str]`，序列化/反序列化由 SQLAlchemy 负责，也不需要额外的读写辅助函数。

### 3.2 新表 `knowledge_point_import_batches`（16 列）

| 分组 | 列 |
|---|---|
| 主键 | `id` |
| 操作与来源 | `user_id`(FK users, SET NULL)、`source_name`、`source_format`、`conflict_strategy`、`status` |
| 计数（全部 NOT NULL + `server_default '0'`） | `total_rows`、`created_count`、`updated_count`、`skipped_count`、`failed_count`、`auto_parent_count` |
| 说明与时间 | `error_summary`、`created_at`、`applied_at`、`rolled_back_at` |

设计要点：

- **批次表不存放导入内容**。被导入的知识点通过 `knowledge_points.import_batch_id` 反向归属，`WHERE import_batch_id = ?` 就是回滚与追溯的唯一查询路径。
- **`user_id` 用 `SET NULL` 而不是 `CASCADE`**：操作人账号被删除后，导入审计必须留存，不能连带消失。
- **计数列 NOT NULL + server_default '0'**：避免「批次存在但读数缺失」的中间态。
- 3 条 CHECK：`status ∈ {applied, failed, rolled_back}`、`conflict_strategy ∈ {skip, update_empty}`、六个计数均 `>= 0`。

### 3.3 约束总览

| 对象 | 名称 | 内容 |
|---|---|---|
| UNIQUE | `uq_knowledge_points_code` | `(code)`，可空 —— 两库唯一索引都允许多个 NULL |
| CHECK | `ck_knowledge_points_difficulty` | `difficulty IS NULL OR difficulty IN ('easy','medium','hard')` |
| CHECK | `ck_knowledge_points_estimated_minutes` | `estimated_minutes IS NULL OR estimated_minutes >= 0` |
| FK | `fk_knowledge_points_import_batch_id` | → `knowledge_point_import_batches.id`，`ON DELETE SET NULL` |
| INDEX | `ix_knowledge_points_import_batch_id` | 按批次反查产物；同时被 InnoDB 复用为 FK 支撑索引 |
| FK | `fk_knowledge_point_import_batches_user_id` | → `users.id`，`ON DELETE SET NULL` |
| INDEX | `ix_knowledge_point_import_batches_user_id` | 按操作人查批次 |
| CHECK ×3 | `ck_knowledge_point_import_batches_*` | 状态机 / 冲突策略 / 计数非负 |

`knowledge_points.parent_id`（归属层级，RESTRICT）与 `knowledge_point_prerequisites`（前置依赖）**均未改动**。

### 3.4 迁移可逆性

**SQLite（本机真实 Alembic 重放，`test_real_sqlite_downgrade_upgrade_roundtrip`）**

```
upgrade 20261001_004 → 批次表存在 + 5 列存在
downgrade 20261001_003 → 批次表消失 + 5 列全部消失
                       且 adoption == "UPGRADE REQUIRED FROM 20261001_003"
                       （该结论只有在「唯一可信 schema 匹配恰好等于 003 冻结合同」时才成立，
                         因此它同时证明了回退后的库是精确合法的 003 形态）
upgrade 20261001_004 → 全部还原，drift errors = 0，unknown_warnings = 0
```

**MySQL（本机无 Docker/MySQL → 离线生成全量 DDL 逐条核对）**

```sql
-- upgrade：5 个 ADD COLUMN + 1 张表 + 1 index + 4 约束，无任何表重建
CREATE TABLE knowledge_point_import_batches ( ... 3 CHECK ... );
CREATE INDEX ix_knowledge_point_import_batches_user_id ON ... (user_id);
ALTER TABLE knowledge_points ADD COLUMN code VARCHAR(64);      -- × 5
CREATE INDEX ix_knowledge_points_import_batch_id ON ... (import_batch_id);
ALTER TABLE knowledge_points ADD CONSTRAINT uq_knowledge_points_code UNIQUE (code);
ALTER TABLE knowledge_points ADD CONSTRAINT fk_knowledge_points_import_batch_id FOREIGN KEY ... ON DELETE SET NULL;
ALTER TABLE knowledge_points ADD CONSTRAINT ck_knowledge_points_difficulty CHECK (...);
ALTER TABLE knowledge_points ADD CONSTRAINT ck_knowledge_points_estimated_minutes CHECK (...);

-- downgrade：顺序正确，无遗留
ALTER TABLE knowledge_points DROP CHECK ...;                       -- × 2
ALTER TABLE knowledge_points DROP FOREIGN KEY fk_knowledge_points_import_batch_id;
ALTER TABLE knowledge_points DROP INDEX uq_knowledge_points_code;
DROP INDEX ix_knowledge_points_import_batch_id ON knowledge_points;
ALTER TABLE knowledge_points DROP COLUMN ...;                      -- × 5
DROP INDEX ix_knowledge_point_import_batches_user_id ON ...;
ALTER TABLE knowledge_point_import_batches DROP FOREIGN KEY ...;
DROP TABLE knowledge_point_import_batches;
```

两个刻意的顺序决定：

1. **先 `CREATE INDEX` 再 `ADD FOREIGN KEY`** —— InnoDB 会直接复用已有索引，不会再自动补一个同列索引（避免 drift 出现多余索引）。
2. **downgrade 时 `DROP FOREIGN KEY` 早于 `DROP INDEX`**（对 `knowledge_points`），与既有 `20261001_002` 的降级写法保持一致 —— 那条路径已在 CI 的 MySQL 作业上验证过。

## 6. 与审计报告 M1 计划的偏差

### 6.1 计划外的必要改动（2 项）

| 项 | 原因 | 影响 |
|---|---|---|
| `app/core/schema_profiles.py` 的 frozen type 表新增 `JSON` | 该表不接受未知类型（抛 `Unsupported frozen type`），不加则 004 合同无法加载，全部 schema 治理测试会失败 | 1 行；纯扩展，不影响任何历史合同 |
| `tests/verify_schema_runtime.py` 新增 MySQL 往返断言 | 满足「downgrade 可逆 / Fresh MySQL 验证」要求，且 SQLite 的 `DROP COLUMN`/`DROP CHECK` 行为与 MySQL 不同，往返必须在 MySQL 上跑 | 24 行；常量基线 `20261001_003`，后续新增 revision 不会让它失效 |

### 6.2 本机无法执行的验证（1 项，必须说明）

**MySQL 上的真实迁移往返没有在本机执行** —— 这台机器没有 Docker，也没有本地 MySQL，无法像 CI 那样起一个空的 `mysql:8.4` 实例重放。

已做的替代验证：
1. 离线生成 upgrade / downgrade **全量 MySQL DDL** 并逐条核对（见 §3.4）；
2. 在 `verify_schema_runtime.py` 里写好真实 MySQL 的往返断言，它会在**下一次 push 触发 CI 时执行**。

**因此本轮唯一未闭环的一环是「MySQL 上的真实执行」，而不是「MySQL 上的 SQL 正确性」。** 若要现在闭环，只需 push 触发 CI（本仓库的 `mysql-schema` 作业就是为此设计的）；本轮按 M1 边界**未 push、未部署**。
