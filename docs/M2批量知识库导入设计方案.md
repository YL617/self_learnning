# 1. 当前系统状态（只读审计结论）

## 1.1 知识点域模型现状

**唯一约束（决定幂等键）**：

```sql
UNIQUE (normalized_subject, normalized_name)   -- uq_knowledge_points_normalized_subject_name
UNIQUE (code)                                  -- uq_knowledge_points_code，允许多个 NULL
CHECK  (difficulty IS NULL OR difficulty IN ('easy','medium','hard'))
CHECK  (estimated_minutes IS NULL OR estimated_minutes >= 0)
FK knowledge_points.parent_id -> knowledge_points.id  ON DELETE RESTRICT
```

> ⚠️ **`parent_id` 是 `RESTRICT`** —— 这意味着「同批次内删父节点」必须**从叶子往根删**，否则被数据库拦住。这是回滚实现的关键约束（§8.4）。

## 1.4 权限与存储设计

- **权限**：M2 的 6 个接口全部挂 `Depends(get_current_admin)`，与既有知识点写接口一致。**无需新权限模型**。
- **存储**：M2 **不落盘**。管理员上传的表格只在请求内解析进内存，请求结束即释放。
  - 这与 `documents` 表的落盘语义完全不同，因此**不复用 `Document` 表**（也避免了为导入文件建 7 天清理任务）。
  - 代价：apply 必须重传数据（§3.2）。
- **体积限制**：`MAX_IMPORT_BYTES = 2 MiB`（表格文本远小于此）；`MAX_IMPORT_ROWS = 500`。

# 2. 开源方案调研

## 2.1 django-import-export ⭐ 思想借鉴 + 反向验证

| 项 | 内容 |
|---|---|
| 链接 | https://github.com/django-import-export/django-import-export |
| 核心机制（源码核实） | `import_data(dataset, dry_run=..., use_transactions=..., rollback_on_validation_errors=..., collect_failed_rows=...)`；`if using_transactions and (dry_run or result.has_errors() or ...): set_rollback(True)` —— **dry_run 与出错走同一条回滚路径**；`import_id_fields` 定义幂等键；`skip_row()` 决定跳过；`Result` 按行返回 `RowResult.diff` |
| 是否引入 | ❌ **不引入**（Django Admin 专属；我们是 FastAPI + SQLAlchemy，引入等于拖进整套 Django） |
| 采纳的设计 | ① 两阶段（dry-run → 确认执行）② 单事务 + 出错即整体回滚 ③ 幂等键 ④ 跳过策略 ⑤ 失败行逐行报告 ⑥ 导入前去重 |
| ⭐ **反向验证** | 其官方文档明确警告：**「如果用户没有走完确认步骤，或在导入中出现错误，临时资源可能不会被删除，需要在生产环境中管理（缓存过期策略或 cron 清理）」** → 这正是我们决定「**preview 不落库、不产生任何临时资源**、批次记录只在 apply 时创建」的外部依据 |
| ⚠️ **反面教训（我们主动避开）** | 其 **bulk 模式**的文档明确说：*「批量操作中异常不与会话行关联」「可能造成部分成功（partially successful import）」「事务可能被留在损坏状态」*。→ **我们不用 bulk**：单批上限 500 行，逐行写入但整体包在一个事务里，**保证「行级错误可归因」+「全有或全无」**，不做「部分成功」 |

## 2.3 openpyxl ⭐ 建议引入（但分批引入）

| 项 | 内容 |
|---|---|
| 链接 | https://github.com/openpyxl/openpyxl · https://openpyxl.readthedocs.io |
| 优点 | 纯 Python、无编译依赖、不增加构建工具链负担；`load_workbook(read_only=True, data_only=True)` + `iter_rows(values_only=True)` 流式读取 |
| 5 个真实坑（已核实，必须写进实现） | ① `read_only` 模式**读不到合并单元格**（只有左上角有值）② `read_only` 下 `ws.max_row` **可能失真**（声明范围被虚报）→ 必须**边迭代边计数** ③ **必须 `wb.close()`**（放在 `finally`），否则 read-only 句柄泄漏直到进程耗尽文件描述符 ④ `data_only=True` 在**公式无缓存结果时返回 `None`**（脚本生成、从未被 Excel 打开保存过的文件）⑤ `.xls`（旧格式）**不支持**，且非 zip 文件会抛 `BadZipFile` → 都要转成清晰的中文 400 |
| ⚠️ 副作用 | 引入它要改 `constraints-prod.lock`（+ `et_xmlfile` 传递依赖）→ **后端镜像重建**。审计报告记录上轮构建约 35 分钟；本轮 M1 部署实测冷构建约 15 分钟 |
| **建议** | **拆成 M2b 单独一发**：把「依赖锁变更」这个**全项目共享、影响面最大**的动作与「导入功能」解耦，风险隔离；M2a 先用 CSV/TSV 把功能闭环（§12） |
| 替代方案 | 不引入 → 上传 xlsx 返回 400 并提示「请在 Excel 里另存为 **CSV UTF-8**（一次点击）」 |

## 2.4 Excel / CSV 导入最佳实践 —— 工程清单（10 条，全部落进实现）

| # | 实践 | 我们的落地 |
|---|---|---|
| 1 | **编码**：中文 Excel 另存 CSV 默认是 **GBK/ANSI**，不是 UTF-8 | 解码顺序：`utf-8-sig` → `utf-8` → `gb18030` → 失败即 400（**顺序不可颠倒**：`gb18030` 能"成功"解码几乎任何字节，放前面会吞掉乱码） |
| 2 | **BOM**：UTF-8 BOM（`EF BB BF`）会变成第一格表头里的 `\ufeff`（显示为 `ï»¿`） | 用 `utf-8-sig` 解码天然剥离；另加一道 `header.lstrip("\ufeff")` 兜底 |
| 3 | **分隔符**：扩展名不可信（`.csv` 可能是分号/制表/竖线分隔） | 有表头 → 按识别到的表头定列；无表头 → 用 `csv.Sniffer` 探测，失败则按扩展名默认（`.tsv`→`\t`，`.csv`→`,`）；探测结果写进 `parse_notes` **回显给管理员** |
| 4 | **引号与嵌入换行**：RFC 4180 要求 `"He said ""ready"""`；生产者不引号会导致**行错位** | 一律用标准库 `csv.reader`（不要自己 `split`）；**列数不齐**的行报 error（这是行错位最可靠的探测器） |
| 5 | **前导零 / 超长数字 ID**：Excel 会把 `007` 变 `7`、>15 位数字变科学计数 | `code` 列**一律按字符串处理**，绝不 `int()`；并在模板下载与页面文案中提示「编码列请设为文本」 |
| 6 | **单元格字符上限 32767**：超长会被 Excel 截断 | `name ≤ 200` / `description` 本期不导入；`aliases` 单项 ≤ 100（与 M1 的 `ALIAS_MAX_LENGTH` 同源） |
| 7 | **CSV/公式注入**：以 `= + - @` 开头的值在 Excel 打开时会被当公式执行 | **我们只读入不导出**，注入风险在**结果 CSV 导出**侧 → 导出时对以 `= + - @ \t \r` 开头的字段加前导单引号 `'`（§7.3） |
| 8 | **日期序列号**：`2026-08-30` 在 Excel 内部是 `45898` | 本期导入**没有日期列**（无 datetime 字段），天然规避；仅需在 xlsx 分支把 datetime 单元格 `str()` 化 |
| 9 | **表头可选**：管理员粘贴时常常不带表头 | 支持「有表头 / 无表头」两种；判据 = 第一行第一格是否命中已知列名集合（`学科/subject/…`） |
| 10 | **空行与空白折叠** | 全空行**静默跳过**并计数进 `parse_notes`；单元格值做 `_collapse_whitespace`（复用 M1 的清洗口径：全角空格 → 半角、连续空白折叠） |

**明确不做**：`pandas`（拖入 numpy）、`csvkit` / `petl` / `tablib`（stdlib `csv` 足够）、`pandera` / `Great Expectations`（我们的校验是领域特定的，Pydantic 更自然）、`OpenRefine`（桌面工具，无法嵌入）。

# 3. 数据流程

## 3.1 两条入口，同一条管线

```
入口 A：粘贴           入口 B：上传
┌──────────────┐      ┌──────────────────┐
│ <textarea>   │      │ <input type=file>│
│ 制表符粘贴    │      │ .csv/.tsv/.xlsx  │
└──────┬───────┘      └────────┬─────────┘
       └───────────┬───────────┘
                   ▼
        ┌──────────────────────┐
        │ ① 解码（编码探测）    │  utf-8-sig → utf-8 → gb18030
        └──────────┬───────────┘
                   ▼
        ┌──────────────────────┐
        │ ② 定界（sniffer）     │  csv.reader / openpyxl.iter_rows
        └──────────┬───────────┘
                   ▼
        ┌──────────────────────┐
        │ ③ 规范成 list[dict]   │  列名归一 + 空白折叠 + 空行剔除
        └──────────┬───────────┘
                   ▼
        ┌──────────────────────┐
        │ ④ 行级校验（10 error  │  纯函数，可脱库单测
        │    + 6 warning）      │
        └──────────┬───────────┘
                   ▼
        ┌──────────────────────┐
        │ ⑤ 整批校验           │  表头结构 / 行数上限 / 成环（内存构图）
        └──────────┬───────────┘
                   ▼
        ┌──────────────────────┐
        │ ⑥ 计划（plan）       │  查库：已存在？父路径已存在？→ create/skip/update_empty/create_parent
        └──────────┬───────────┘
                   ▼
        ┌──────────────────────┐
        │ ⑦ 写库（仅 apply）    │  单事务：先建父节点（拓扑序）→ 再建/更新目标知识点
        └──────────┬───────────┘
                   ▼
        ┌──────────────────────┐
        │ ⑧ 落批次记录         │  knowledge_point_import_batches
        └──────────────────────┘
```

**管线复用**：`preview` 与 `apply` **调用完全相同的 `_parse → _validate → _plan` 三个纯函数**，唯一差别是 `apply` 在最后多一步 `_write()`。这保证「预览所见 = 执行所得」，也是 TOCTOU 防护的基础（§7.2）。

## 3.2 两阶段时序（preview 不落库）

```
管理员         前端                     后端                      数据库
   │  粘贴/上传  │                        │                         │
   ├────────────►│  POST /preview         │                         │
   │             ├───────────────────────►│  解析+校验+查库计划      │──► SELECT ×3
   │             │                        │  ◄────── 只读 ──────────┤
   │             │◄── 预览 JSON ──────────┤  ⚠️ 不写任何表           │
   │  看预览     │  (计数/错误行/环/父节点)│  ⚠️ 不建批次             │
   │             │                        │  ⚠️ 不落盘临时文件       │
   │  选策略     │                        │                         │
   │  二次确认   │                        │                         │
   ├────────────►│  POST /apply           │                         │
   │             │  (重传同一份数据 +      │  ① 重新 解析+校验+计划   │
   │             │   conflict_strategy +  │  ② 任一行 error → 409    │
   │             │   expected_total_rows) │     ── 不写任何数据 ──   │
   │             │                        │  ③ 通过 → 单事务写入     │──► BEGIN
   │             │                        │     父节点(拓扑序)       │──► INSERT
   │             │                        │     目标知识点           │──► INSERT/UPDATE
   │             │                        │     批次记录             │──► INSERT batch
   │             │                        │                         │──► COMMIT
   │             │◄── 执行报告 + batch_id ─┤                         │
```

> **为什么 apply 必须重传数据**：因为我们**刻意不在服务端暂存**（不落盘、不建 Redis 键、不建批次行）。这是 django-import-export 官方警告所指向的坑——它引入了「临时资源生命周期管理」这个额外问题，而我们直接**把它消灭掉**。代价只是前端持有原始文本/`File` 对象再传一次。

## 3.3 解析层设计

```python
# app/services/knowledge_import.py（新增，纯函数优先）

MAX_IMPORT_ROWS = 500
```

## 3.4 幂等与父节点自动创建

**幂等键**：`(normalized_subject, normalized_name)` —— 与 DB 唯一约束 `uq_knowledge_points_normalized_subject_name` **完全同源**，复用 M1 的 `clean_name` / `normalize_subject` 口径（全角空格 → 半角、连续空白折叠、拉丁字母小写）。

| `conflict_strategy` | 命中已存在知识点时的行为 |
|---|---|
| `skip`（默认） | **完全不动**已有行（保护人工修正成果），计 `skipped_count` |
| `update_empty` | **只填充原值为 NULL 的字段**（`code`/`aliases`/`difficulty`/`estimated_minutes`/`description`/`parent_id`），**绝不覆盖已有非空值**，计 `updated_count` |

> **没有 `overwrite` 策略。** 理由：R5（批量误操作写坏数据）。要改已有值，走单条编辑页。

**父节点自动创建**：

```
输入路径 "线性表>栈"  →  拆成 ["线性表", "栈"]
对 segments 逐层：
  查 (subject, 当前层名) 是否存在？
    存在 → 复用其 id 作为下一层的 parent
    不存在 → 标记为「将自动创建」，暂不写库（preview 阶段）
末尾 segment 即本行知识点名 → 若与路径末段同名，则本行知识点本身就是最后一段
```

- 自动创建的父节点：`source = KP_SOURCE_ADMIN`、`status = active`、`import_batch_id = 本批次`、无 `description`。
- 计 `auto_parent_count`。
- **父节点也受批内去重**：两行写 `A>B` 与 `A>C`，`A` 只建一次。
- **跨学科拒绝**：`parent_path` 指向的已存在节点若属于别的 `normalized_subject` → 该行 **E08 error**（复用 `_assert_parent` 的语义）。

# 6. 数据校验规则

## 6.1 行级 error（E01–E10，命中即该行不可导入）

| 码 | 名称 | 判据 | 文案示例 |
|---|---|---|---|
| `E01` | `EMPTY_SUBJECT` | 学科为空（清洗后） | 第 12 行：学科不能为空 |
| `E02` | `EMPTY_NAME` | 知识点名为空（清洗后） | 第 12 行：知识点名称不能为空 |
| `E03` | `TOO_LONG` | `name > 200` 或 `subject > 100` | 第 12 行：知识点名称超过 200 个字符 |
| `E04` | `CODE_TOO_LONG` | `code > 64` | 第 12 行：编码超过 64 个字符 |
| `E05` | `INVALID_DIFFICULTY` | 不在 `easy/medium/hard`（先做中文映射） | 第 12 行：难度只能是 easy / medium / hard（或 简单 / 中等 / 困难） |
| `E06` | `INVALID_MINUTES` | 非整数 / `< 0` / `> 100000` | 第 12 行：预计学时必须是不小于 0 的整数分钟 |
| `E07` | `INVALID_ALIAS` | 单项 `> 100` 字符 或 超过 20 项 | 第 12 行：别名最多 20 个，单个不超过 100 个字符 |
| `E08` | `PARENT_SUBJECT_MISMATCH` | `parent_path` 指向的**已存在**知识点属于其他学科 | 第 12 行：父知识点「栈」属于学科「算法」，与「数据结构」不一致 |
| `E09` | `DUPLICATE_IN_BATCH` | 批内 `(normalized_subject, normalized_name)` 重复（**保留首次出现**，后续重复行报错并给出首次行号） | 第 20 行：与第 12 行重复（同一学科下同名知识点） |
| `E10` | `PARENT_SELF_REFERENCE` | `parent_path` 末段 == 本行 `name`（自己当自己的父） | 第 12 行：层级路径不能把知识点自己作为父级 |

> `E10` 是**行内可判**的自引用；**跨行的环**是整批级 `B04`（§6.2）。二者不能混为一谈——逐行校验永远发现不了 `A>B` + `B>A`。

## 6.2 整批级 error（B01–B04，命中即整批拒绝）

| 码 | 名称 | 判据 | 处理 |
|---|---|---|---|
| `B01` | `PARSE_FAILED` | 编码不可识别 / 非 zip 却当 xlsx / `.xls` 旧格式 / 空文件 / 无任何数据行 / 二进制噪声 | `400`，`batch_errors` 给出具体原因 |
| `B02` | `HEADER_INVALID` | 缺少必需列（`subject` 或 `name`）· 表头列名**重复** · 声明了表头但列数 < 3 | `400` |
| `B03` | `TOO_MANY_ROWS` | 数据行 `> 500` | `400`，文案给出实际行数 |
| `B04` | `CYCLE` | **把整批行的 `parent_path` 关系并入现有 `parent_id` 邻接表后，检出环** | `409`，**必须指出参与环的完整路径链**（如 `数据结构 > 栈 → 线性表 → 栈`） |

**成环检测实现要点**（这是 M2 技术含量最高的一段）：

```
1. 构造图：节点 = (subject, normalized_name) 的并集（既有的 + 本批新增/自动创建的）
   边 = child → parent（来自 parent_path 逐层关系 + 本批行与其父的关系）
2. 现有边只需加载「涉及的 subject」下的 parent_id（不做全表扫描）
3. 对每个新涉及的节点做 DFS，带 path 栈 → 一旦回到栈内节点即成立，回溯出环路径
4. 检出环 → 整批拒绝（B04），环路径原样返回给前端高亮
```

> 只做「逐行父节点校验」是**不够的**：`A>B`（父 B）与 `B>A`（父 A）两行各自合法，合起来成环。这正是设计里反复强调「整批成环检测」的原因。

## 6.3 warning（W01–W06，**不阻断**，仅提示）

| 码 | 名称 | 判据 | 为什么是 warning 而不是 error |
|---|---|---|---|
| `W01` | `NEW_SUBJECT` | 该学科在库中尚不存在 | 学科是自由字符串，不是实体；建新的完全合理 |
| `W02` | `AUTO_PARENT` | 该行会导致**自动创建父节点** | 自动创建是正常功能，但管理员应当**知情** |
| `W03` | `EXISTING_SKIP` | 命中已存在知识点（`skip` 将跳过 / `update_empty` 将补空） | 幂等命中是**预期行为**，不是错误 |
| `W04` | `DEEP_HIERARCHY` | 层级路径深度 `> 4` | 过深的层级不利于推荐与展示，建议扁平化，但不阻断 |
| `W05` | `ALIAS_CROSS_ROW` | 该行别名与其他行的**名称或别名**重复 | ⭐ **这是 M1 有意留到 M2 的跨行别名检查**（R10）。**M2 只以 warning 暴露，不做合并/拒绝** —— 因为自动合并会误伤（如「栈」既是数据结构也是函数调用栈）；真正的治理放到 M6 质量体检 |
| `W06` | `MISSING_METADATA` | 未提供 `difficulty` 且未提供 `estimated_minutes` | 不影响正确性，但推荐与展示会退化 |

**`parse_notes`（非校验结论，仅解析事实回显）**：编码回退到 `gb18030` / 探测到的分隔符 / 剔除的空行数 / xlsx 含多个 sheet（**只读第一个并在 notes 里明说**）/ 公式单元格无缓存值（`data_only` 返回 `None`）。

# 7. 错误处理

## 7.1 策略：**全有或全无（abort）**，不做「部分成功」

> **这是本方案一个需要你确认的决策点。**

| 策略 | 行为 | 采纳 |
|---|---|---|
| **abort（默认，M2 只实现这个）** | 存在**任何** error → 整批拒绝，**零写入** | ✅ |
| `skip_rows`（跳过错误行，导入正确行） | 部分成功 | ❌ **M2 不做** |

**理由**：① 单事务语义下「部分成功」会让批次计数、`status`、回滚范围三者纠缠不清；② django-import-export 的 bulk 模式文档已明确警告「部分成功」与「事务可能被留在损坏状态」；③ 修正 1 行重新提交的成本极低；④ 与 R5（批量误操作）立场一致。

**管理员体验补偿**：`preview` 一次性列出**所有**错误行的码、字段、文案与行号，前端支持「只看错误行」与「下载结果 CSV」，改完再传一次即可。

## 7.2 TOCTOU 防护（R6）

| 风险 | 触发 | 防护 |
|---|---|---|
| preview 与 apply 之间库被改动（双管理员并发） | A 预览 → B 导入 → A 执行 | `apply` **完整重跑** `_parse → _validate → _plan`；出现**任何新 error** → `409` 并要求重新预览 |
| 预览了 A 文件、执行了 B 文件 | 前端状态错乱 | `expected_total_rows` 比对，不一致 → `409` |
| 同一批并发提交两次 | 双击 | 单事务 + 唯一约束兜底；第二次必然撞 `uq_knowledge_points_normalized_subject_name` → 整批 `409`（脏写不可能发生） |

## 7.3 写入期异常（`status='failed'`）

```
try:
    with db.begin_nested() if not outer else ...:   # 复用既有 session 事务
        _write(...)      # 父节点 → 目标知识点 → 更新批次
except Exception as exc:
    db.rollback()        # 全批回滚，零写入
    # 单独用一个"新事务"写失败批次行（关键：不能被刚回滚的事务带走）
    _record_failed_batch(db, exc, rows)
    raise HTTPException(409, "导入失败，已整体回滚：{exc}")
```

**要点**：失败批次记录**必须在回滚之后用新事务单独写入**，否则「批次表里看不到这次失败」——这正是需要 `status='failed'` 这个枚举值的原因（M1 已经把它放进 CHECK 了）。

`error_summary`（`Text`，M1 已有）存**供人读的摘要**（如「3 行失败，首个错误：第 12 行 知识点名称不能为空」），**不存全量行数据**。

**结果 CSV**：**不落盘、不进服务端**。由前端根据 `rows` 在浏览器本地生成 `Blob` 下载。这样既满足「下载本批结果」，又完全避免临时文件生命周期问题。
- 导出时对以 `= + - @ \t \r` 开头的字段**加前导单引号**（CSV/公式注入防护，§2.4-⑦）。

# 8. 回滚方案

## 8.1 三层回滚，粒度递增

| 层 | 机制 | 可回滚范围 |
|---|---|---|
| L1 **事务回滚** | 单事务 + 异常即 `rollback()` | 写入期任何异常 → **零写入** |
| L2 **apply 前拒绝** | 重新校验发现 error → `409` | 不进入写入 |
| L3 **批次回滚** | `POST /batches/{id}/rollback` | 事后撤销**本批新建的**知识点 |

## 8.2 L3 前置检查（`blocking_references`）

对本批次所有知识点（`import_batch_id = id`）逐一检查 **4 类引用**：

| 引用 | 来源 | 判据 |
|---|---|---|
| `has_children` | `knowledge_points.parent_id` | 有子节点**且该子节点不属于本批** |
| `linked_question` | `question_knowledge_points` | 任一关联即阻止 |
| `has_mastery` | `user_knowledge_point_mastery` | 任一掌握度记录即阻止 |
| `prerequisite_edge` | `knowledge_point_prerequisites` | 任一方向（`kp` 或 `prereq`）即阻止 |

**任一命中 → 整批拒绝回滚**（`409`），返回 `blocking_references` 完整清单，**不做部分回滚**。
理由与既有 `KnowledgePointService.delete()` 的 4 道预检**完全一致**（复用同一组语义，不另立规则）。

## 8.3 只删「本批新建」，`update_empty` 的填充**不清空**

| 知识点类别 | 回滚行为 |
|---|---|
| 本批 `created` 的 | ✅ 删除 |
| 本批自动创建的**父节点** | ✅ 删除（若未被本批之外引用） |
| 本批 `updated`（`update_empty` 填充过）的 | ⛔ **保留**，仅计 `kept_updated_count` 并在响应里明示 |

> ⚠️ **必须写明的局限**：`update_empty` 给原为 `NULL` 的字段填了值，但 M1 的批次表**没有字段级快照列**（改成有快照需要新 migration，与「M2 零 DB 变更」冲突）。
> 因此 **M2 的批次回滚无法把「被填充的字段」还原成 `NULL`**。
> **补偿措施（三重）**：
> ① 响应里返回 `kept_updated_count`，前端二次确认弹窗明确写「本批有 N 条是**补充空字段**，回滚不会清空这些补充内容」；
> ② `docs` 与页面上都写明；
> ③ **默认策略是 `skip`**（完全不动既有数据），`update_empty` 是需要管理员主动选择的。
>
> **后续增强（记入 M6/独立任务）**：新增 `knowledge_point_import_batch_items` 明细表（含 `before_values` JSON 快照）即可实现字段级可逆——但那是**独立 migration + 治理链路**，不该塞进 M2。

## 8.4 删除顺序：**从叶子到根**（关键实现细节）

`knowledge_points.parent_id` 是 **`ON DELETE RESTRICT`**。若同批次内既有父又有子，顺序错误会被数据库直接拦下（`IntegrityError`）。

```
1. 取本批待删集合 S（created + 自动创建父节点，且未被外部引用）
2. 在 S 内部构图，按「深度降序」排序（等价于拓扑逆序）
3. 逐层删除：先删所有叶子（无子节点），再删其父，直到 S 清空
4. 若 S 内存在环（理论上已被 B04 挡在导入前）→ 直接 raise，不尝试删除
```

## 8.5 回滚后状态

- 批次行：`status = 'rolled_back'`、`rolled_back_at = now()`、计数列**保持不变**（保留「本批曾导入了多少」的历史事实，与 `status` 一起构成完整审计）。
- 被删知识点的 `import_batch_id` 随行消失，无需清理。
- **回滚不可再回滚**（无「撤销回滚」），前端二次确认。
