## 0. 结论摘要

### 0.1 一句话诊断

> **P4-3 的瓶颈不是"生成 50 道题"，而是"让 50 道题可信、并且真正落到生产库"。**
> 前者是脚本问题（约 2.5 人日），后者被一个此前未被单列的**硬依赖**卡住：**P4-3 Apply 必须以一次完整生产部署为前置**（生产库尚无 `review_status` 列，新代码也未上线）。

### 0.2 关键因果链

```
生产 documents = 0 / knowledge_chunks = 0
   └─▶ POST /questions/generate 的 grounding 来源为空（取 Document+KnowledgeChunk，最多 8 段）
        └─▶ AI 出题只能依赖「系统提示词 + 知识点名」
             └─▶ 质量下限低（KMLE 研究：幻觉 / 多解 / 关键假设缺失）
                  └─▶ 人工审核不是「可选项」，是唯一效度闸门
                       └─▶ 审核产能 = 真正的瓶颈（50 题 × 人工）

生产 questions.review_status 列不存在（alembic 仍 007）
   └─▶ 新代码（P4-1/P4-2/P4-2.5）未部署
        └─▶ POST /admin/questions 走 ORM 会带 review_status → 生产上报 1054 Unknown column
             └─▶ 【硬约束】P4-3 Apply 之前，必须先完成一次生产部署（含 DB migrate 008）
```

### 0.3 三个必须做 / 三个坚决不做

| ✅ 必须做 | ⛔ 坚决不做 |
|---|---|
| 把「结构校验 + 确定性质量门禁」写成**可复现脚本**，与生成解耦 | 不做：为出题新增后端端点 / 改 DB / 改 models |
| 生成与 Apply **分两段**：先出离线 manifest，人工清单审核后再逐条写库 | 不做：把生成脚本放进生产容器跑（写操作 + 1.6 GiB OOM 风险） |
| 把「相似度去重」补上（现有代码只有精确 stem 去重） | 不做：批量直连 DB 写 `source='ai'`（绕过 `attach()` 关口） |

### 1.3 审计问题逐条回答

**Q1：现有出题能力能直接复用吗？**

| 能力 | 结论 | 依据 |
|---|---|---|
| LLM 调用 | ✅ 复用 `AIModelGateway.generate_json()` | 支持 deepseek/qwen/glm，key 走 settings |
| 出题 prompt | ✅ 复用 `generate_questions()` | 已含"变体题"约束与解析 ≥60 字要求 |
| 结果归一化 | ✅ 复用 `_normalize()` | 校验 `stem` 非空、options 为 list |
| **去重** | ⚠️ **只做精确 stem 去重**（`seen` 集合） | 语义近似题**不会被拦** → 需补相似度去重 |
| **解析质量信号** | ⚠️ **被 `_ensure_analysis()` 污染** | <40 字解析会被自动补全 → 门禁须读**原始** analysis |
| 绑定知识点 | ✅ 走 `QuestionKnowledgePointService.attach()` | concept-only / 学科一致 / primary 唯一 / 幂等 |
| 落库 | ❌ `POST /questions/generate` 存为**当前用户私有** | 不适用于共享题库生产 |

**Q2：是否有现成的批量/导入范式可复刻？**

✅ 有，且非常完整 —— `app/services/knowledge_import.py` 提供了本项目已验证的工程范式：

```
parse_pasted / parse_uploaded  →  validate_rows  →  plan_import
   →  preview_rows（人工看）  →  apply_import（批次留痕）
   →  collect_blockers / rollback_batch
常量：MAX_IMPORT_BYTES=2MB、MAX_IMPORT_ROWS=500、PREVIEW_ROW_LIMIT=200
```
**但 P4-3 不新增导入入口**（用户已选"一次性脚本"）→ 只**借用其"preflight → manifest → 人工确认 → 逐条写 → 留痕 → 可回滚"的纪律**，不引入新的 xlsx 上传端点。

**Q3：管理端能承担审核工作台吗？**

❌ 目前不能。`AdminQuestionsView.vue` 只调用 `createQuestion / getQuestion / deleteQuestion / knowledgeCoverage / questions / knowledgePoints.list`；**全前端对 `submit-review/approve/reject/publish/archive` 与 `review_status` 的消费数 = 0**。
→ 与"脚本驱动审核"决策一致；但登记一条**一致性缺口**：管理端页面此刻看不到审核态（非阻塞，建议并入 P4-4）。

**Q4：依赖真相？**

- ✅ `openpyxl>=3.1.0` **确实已在** `requirements.txt`（注释说明由 `constraints-prod.lock` 固定 3.1.5）。
  > 📌 **更正**：技术资料里"没有 openpyxl"的旧结论**已过时**，以本行为准。
- ✅ `python-multipart>=0.0.9` 在（文件上传能力现成）。
- ❌ 无 `pandas` / `chromadb` —— 与本设计无关（不引入）。
- **结论：P4-3 不需要新增任何依赖。**

**Q5：AI 网关的静默降级会不会污染批量结果？**

会，且有**两条**路径：`chat()` 在「无 api_key」与「请求异常」时都返回 `_offline_reply()` 模板文本；`extract_json()` 解析失败 → `generate_json()` 返回 `{}` → `generate_questions()` 抛 `RuntimeError("AI 服务暂不可用")`。
→ 无法区分"模型真没结果"与"离线降级"。**批量脚本必须保留原始响应文本并显式判定**，禁止把 0 题当正常结果静默跳过。

### 2.2 七问分析表

**① AQuAP / Item Factory（Duolingo）**

| 问题 | 回答 |
|---|---|
| ①解决什么 | 大规模 AI 命题的**质量与题库健康度**监控 |
| ②输入 | SME 蓝图 / 任务族；候选题池的运行数据 |
| ③输出 | 筛查结果、人工评审队列、题库健康度指标（有效题库规模 EBS、最大曝光度、罕见施测比例） |
| ④需要多少数据 | **不需要**用户作答数据即可做质量筛查；健康度指标需要施测数据 |
| ⑤适不适合我们 | **高度适合**（流程层） |
| ⑥改造成本 | 低（只借流程） |
| ⑦能否直接引入 | 引入**流程**，不引入平台 |

→ **采纳**：`生成 → 自动筛查（长度/语法/拼写/格式/基本效度）→ 人工 Item Quality Review（+公平性）→ 试测 → 上线`。
核心洞见（原文）：**"流利度易自动化，效度不能"** —— 生成的题"读起来像题"不代表"测得住"。

**② AIG 综述（自动命题全貌）**

| 问题 | 回答 |
|---|---|
| ⑤适不适合我们 | 适合，用于校准我们的期望 |
| ⑦能否直接引入 | 只取结论 |

→ **采纳三条结论**：
1. "生成题必须依据**显式测量标准**评估，而不只是表面合理性" → 门禁必须是**确定性规则**，不能只靠"看起来像题"。
2. 运营型 AIG 的完整链路 = 生成 + **筛查** + 人工评审 + 试测 + 校准 + 上线后监控；"筛查"不是可省的辅助环节。
3. 效度的主要敌人是**幻觉与多解**（医学题干"临床风格但含幻觉疗法/矛盾化验值"）→ 人工评审不可省。

**③ KMLE 论文（可直接抄的校验清单）**

| 问题 | 回答 |
|---|---|
| ⑤适不适合我们 | **最直接可落地的一篇** |
| ⑥改造成本 | 极低（规则可逐条实现） |
| ⑦能否直接引入 | 引入**检查项**，不引入医学领域内容 |

→ **采纳其自动校验项**（本报告 §3.2 的规则来源）：
- 结构类：正向前导问法、选项 A–E 同质、按长度排序、单一可辩护正确答案、**禁用"全选/全不选"**、题干不得含否定式
- 一致性类：**key-option 冲突**、**多个可辩护答案**、**选项互不排斥**、无意外提示（**选项长度偏差 / 答案位置偏差**）
- 全库级：**n-gram 与语义相似度去重**（防重复题）
- 流程：4 段式（自动检查+批评 → 仅对失败项**定向重生成** → 重新评估 → 人工终审）；人工 ≥2 名专家
- **"验证优先"原则**：AI 校验是"进入题库前的关口"，**永不替代**专家评审

**④ Frontiers 论文（计算机专业课的实证）**

| 问题 | 回答 |
|---|---|
| ①解决什么 | LLM 生成题的心理测量质量是否等于人工题 |
| ④需要多少数据 | 需要学生作答数据（n≈数百） |
| ⑤适不适合我们 | 结论适合，**方法暂不适合**（我们暂无作答数据） |
| ⑦能否直接引入 | 结论 + 校验流程 |

→ **采纳**：
1. 在**操作系统课（计算机专业）**上，LLM 生成 MCQ 与人工 MCQ"**无显著心理测量差异**" → 我们选「数据结构」是可行的，不必因"没有教材"就否定路线。
2. 三道 SME、两轮校验：第一轮查（题干指令是否清晰 / 选项是否含意外线索 / 是否与教学目标一致），第二轮**实际解一遍**（干扰项是否"错但可信"、正确项是否可由题干明确推出）。
3. 反面案例：被判 reject 的题"初看很规整，实际解一遍才发现**关键假设未陈述**，导致多个选项都说得通" → **必须实际解题**，不能只读题。
4. 若未通过校验 → 弃用整轮生成，重新生成（不做局部修补）。

**⑤ AIR 经验教训（工程侧的坑）**

→ **采纳**：即使写了详尽 prompt，仍出现 **redundant items（重复题）**；质量检查必须同时覆盖内容与**长度/格式**；需做**心理测量试测**；关注内容安全与透明度。
→ 对我们的直接含义：**去重必须升级为相似度级**（见 §3.2 G4）。

**⑥ QTI 3.0**

①解决题库跨系统交换；②输入 XML 内容包；④无需数据；⑤**信息模型高度相关**；⑥全套实现成本极高；⑦**只借信息模型**。
→ **采纳**：`assessmentItem`↔`questions`、`responseDeclaration`↔`answer`、`responseProcessing`↔`check_answer`、**item 统计元数据（难度/曝光）**↔ 未来 `difficulty` 与使用统计。**不引入 XML / 内容包 / 30+ 交互类型**。

**⑦ HITL**

→ **采纳**：「确定性阻断规则 + 置信度阈值 + 转人工队列」。落到本项目 = 门禁脚本（确定性）→ 人工清单审核 → approve/reject。

### 2.3 三条可直接落地的结论

1. **门禁必须是确定性规则集，且包含"实际解题"式检查**（答案 ↔ 选项可对齐、key-option 冲突、多解）；仅靠 LLM 自评不够（KMLE 明确：AI 自评不可替代人工）。
2. **相似度去重是行业共识动作，我们目前缺**（现有只有精确 stem 去重）→ P4-3 必须补，否则 50 题里出现近似重复的概率随规模上升。
3. **"发布前必须过审"有外部背书**（QTI item 元数据、AQuAP 筛查+评审、HITL 转人工）→ P4-2/P4-2.5 的双轴模型方向正确，P4-3 只是把它用起来。

## 3. 第三步：方案设计

### 3.1 方案 A · 生成管道形态（四段式，零后端改动）

```
┌─ A1 生成（离线·本地 venv）──────────────────────────────────┐
│  输入：目标 concept 清单（id + name + 难度配额）             │
│  动作：逐 concept 调 generate_questions(subject, concept名,  │
│        count, question_type) —— 复用现有实现                 │
│  产出：raw 响应留存（含失败/离线降级判定）                    │
└──────────────────────────────┬───────────────────────────────┘
                               ▼
┌─ A2 门禁（离线·确定性规则，§3.2）──────────────────────────┐
│  G1 结构 → G2 答案对齐 → G3 解析原始长度 → G4 去重          │
│  → G5 选项质量 → G6 元数据 → G7 学科/节点类型(预期0)         │
│  → G8 离线降级判定                                          │
│  产出：docs/M5.5_P4-3_题目供给清单.json                     │
│        （每题：concept/difficulty/stem/options/answer/       │
│          analysis/门禁明细/建议动作）                        │
└──────────────────────────────┬───────────────────────────────┘
                               ▼
┌─ A3 人工清单审核（表格化，逐条 accept / reject / edit）────┐
│  【停点】必须由你确认后才进入 A4                             │
└──────────────────────────────┬───────────────────────────────┘
                               ▼
┌─ A4 Apply（逐条 API 写库，[需批准]）───────────────────────┐
│  前置：生产已部署（含 DB migrate 20261010_007→20261012_008）  │
│  逐条：POST /api/v1/admin/questions                          │
│        （visibility="private" + knowledge_point_ids=[cid]）   │
│        → HTTP 201，记录 question_id                           │
│  逐条：POST /admin/questions/{id}/submit-review → approve     │
│        → publish（publish 是置 shared 的唯一入口）            │
│  留痕：Apply 报告（id 清单 / 每题 concept / HTTP 码）         │
│  回滚：记录 id 清单 → 逐条 DELETE（或 archive 归档）          │
└──────────────────────────────────────────────────────────────┘
```

**关键设计选择**

| 选择 | 理由 |
|---|---|
| 生成**不**放进生产容器 | 生产仅 1.6 GiB、曾多次 OOM；生成是写操作前的最脏环节，隔离在本地 |
| 落库用 `visibility="private"` 再 `publish` | `publish` 是"置 shared 的唯一入口"（P4-2 不变量），显式遵守而非绕过 |
| 一题一个 primary concept | 沿用 M5 Step5 规则，**不引入 secondary**（避免覆盖统计口径漂移） |
| 全部走 `POST /admin/questions` | 该端点内部调 `attach()` → concept-only + 学科一致 + primary 唯一 由既有服务保证 |
| 用 manifest 而非直接写 | 沿用 V1.2 导入纪律：`preflight → 清单 → 人工确认 → 逐条写 → 验证` |

### 3.2 方案 B · 质量门禁规格（P4-3 的核心产物）

| ID | 规则 | 阈值 | 依据 | 预期命中 |
|---|---|---|---|---|
| **G1** | 结构完整性：`stem` 非空且 12–400 字；`answer` 非空；`choice` → `2 ≤ options ≤ 6`；题型 ∈ {choice, fill} | 见左 | 现 schema 上限 | 低 |
| **G2** | **答案可对齐**：`choice` → `answer` 首字符 ∈ 选项首字母集合 | 严格 | KMLE「单一可辩护正确答案」 | 中 |
| **G3** | **解析原始质量**：`analysis`（**`_ensure_analysis` 之前**）≥ 60 字，且**不含**补全指纹「复习提示：请结合」 | 60 字 | 复用 prompt 自述要求；防补全掩盖 | 中 |
| **G4** | **去重（两级）**：① 归一化（去空白/标点、全角→半角、小写）后精确比对；② 字符 3-gram Jaccard ≥ 0.80 判重。比对范围 = **现有 8 题 ∪ 同批全部题** | 0.80 | KMLE「n-gram+语义去重」；AIR「redundant items 是主要质量问题」 | **高**（现有代码零防护） |
| **G5** | **选项质量**：① 禁用「以上都对/都不对/以上皆是/均正确」；② 选项长度极差比 ≤ 2.5；③ **批内正确答案位置分布** A/B/C/D 各占 20%–30% | 见左 | KMLE「选项长度偏差 / 答案位置偏差」「选项同质」 | 中 |
| **G6** | **元数据完备**：`knowledge_point` 自由文本 = **concept 名**（非章名）；`difficulty` ∈ {easy, medium, hard} 且非 NULL | 严格 | 修正现存值全为「栈和队列」的缺陷；复用全项目唯一难度词表 | 低 |
| **G7** | 学科一致 / 节点类型 = concept | 由 `attach()` 保证 | M4 既有关口 | **预期 0**（写明：若 >0 说明绕过了服务） |
| **G8** | **离线降级判定**：`generate_json` 返回 `{}`、`generate_questions` 抛错、或 0 题 → 记为 `error`；**禁止静默跳过** | 严格 | `AIModelGateway` 两条静默降级路径 | 视网络 |

**门禁输出契约**：每题携带 `gate_results: {G1: pass/fail+原因, ...}`，任一 `fail` → `建议动作=reject`；`G4` 命中 → 标 `duplicate_of: <id>`。

> 📌 **G3 与 G4 是本方案相对现有代码的**净增量**：`generate_questions()` 目前既不检查原始解析长度，也只做精确 stem 去重。

### 3.3 方案 C · 覆盖目标（50 题 / 27 concept）

| 批次 | 题量 | 目标 concept | 累计题量 | 累计覆盖 | 目的 |
|---|---|---|---|---|---|
| **批 1（试点）** | 20 | 前置度 ≥ 4 的 **8 个**（46,34,9,11,13,36,67 + 19） | 20 | 8 | **跑通全链路**：生成→门禁→审核→Apply→用户作答→mastery 写入 |
| 批 2 | 20 | 前置度 2–3 的 **12 个**（6,38,4,16,29,30,32,48,57,60,62,63） | 40 | 20 | 覆盖全部章节枢纽 |
| 批 3 | 10 | 前置度 2 的余下 3 个（69,72,25）+ **排序族 deg=1 的 4 个**（73 快速排序,76 堆排序,77 归并排序,70 希尔排序） | **50** | **27** | 补齐排序/查找高频考点 |
| 合计 | 50 | — | 50 | **27 / 56 = 48%** | 达成 §6 首期目标（≥20~30 concept） |

**分配规则**：批 1 每 concept 2 题；批 2 每 concept 1–2 题；批 3 排序族每 concept 1 题。
**难度配额**：`easy : medium : hard ≈ 3 : 5 : 2`（对齐 §6 建议）。
**题型配额**：`choice` 为主（≥ 80%），`fill` 为辅。

### 3.4 方案 D · 审核与发布脚本

| 组件 | 形态 | 说明 |
|---|---|---|
| `scripts/p43_generate.py` | 一次性脚本（本地 venv） | 按 concept 清单生成 → 门禁 → 写 manifest；**只读生产 + 只写本地文件** |

**审核的"人工门槛"（最低集，来自 §7.3 + KMLE 落地版）**
