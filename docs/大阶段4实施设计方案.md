## 0. 一句话结论

本阶段**不新建任何已有模块**，只做三件事：

1. **给 `knowledge_points` 补 4 个字段 + 1 个追溯列**（`description` 已存在，不重复加），让知识点从「一个名字」变成「可被机器使用的内容单元」；
2. **补两条内容生产管线**：管理员批量导入（阶段一）+ AI 辅助标注（阶段二）；
3. **补两层质量与消费**：知识质量体检（阶段三）+ 推荐上下文（阶段四），最后收口到两个后台页面（阶段五）。

关键约束：**推荐引擎（V1）、掌握度算法、前置 DAG、题目知识点关联表，一律不改语义，只做向后兼容的增强。**

### 1.2 五个关键审计结论

1. **`description` 已存在**（`Text NULL`），用户列出的 5 个字段中这个**不需要新增**，只补 `code` / `aliases` / `difficulty` / `estimated_minutes`。

## 2. 分阶段新增能力

## 阶段一：知识库生产能力升级

### 2.1 知识点扩展字段设计

**设计原则：每个字段都必须回答「它解决了哪个具体问题」，否则不加。**

| 字段 | 类型 | 为什么必须加（价值） | 不加会怎样 |
|---|---|---|---|
| `code` | `VARCHAR(64) NULL` + `UNIQUE` | **稳定标识**。名称可以改名、可以纠错，但编码不变；导入对账、跨批次幂等、未来与外部标准（如教材目录 / CASE `humanCodingScheme`）对齐都靠它。 | 只能靠名称做身份，改名即断链；重复导入无法可靠幂等 |
| `aliases` | `TEXT NULL`（JSON 数组字符串） | **防同义名分裂**。没有它，`栈` / `堆栈` / `stack` 会被建成 3 个知识点，掌握度被拆成 3 份，学生永远「达不到掌握」，推荐粒度也被打碎。同时它是 AI 标注的召回词表。 | **掌握度系统会长期失真**（这是最贵的一条） |
| `difficulty` | `VARCHAR(32) NULL` | 供推荐排序、时长估算、难度梯度布题使用。**复用既有词汇 `easy / medium / hard`**（与 `plan_items.difficulty`、`mastery.DIFFICULTY_WEIGHTS` 同源），**不引入第二套难度语义**。 | 推荐只能按掌握度盲排，无法「先易后难」 |
| `estimated_minutes` | `INT NULL` | 阶段四明确要求 `RecommendationContext` 含「学习时间」；用于每日计划的时长预算与「今天能学完几个」的判断。 | 今日建议无法给出可用时长，学生无法规划 |
| `import_batch_id` | `INT NULL` + FK→`knowledge_point_import_batches.id` `ON DELETE SET NULL` | **追溯与回滚**。支撑「本次导入建了哪些知识点」「误导入能否撤回」。 | 「失败回滚」无法实现 |
| ~~`description`~~ | 已存在 | 不改 | — |

**为什么 `aliases` 不做成独立别名表？**

- 规模是 10²~10³，服务层把知识点全量载入内存做归一化匹配是可接受的（推荐引擎本来就是全量载入）；
- 独立表需要额外 JOIN、额外迁移、额外 Service，而**别名唯一性仍然无法只靠 DB 约束完全表达**（别名可能同时是另一个知识点的正式名）；
- 因此别名唯一性由**服务层 + 质量报告**（§2.3）双重保障。若未来规模上万，再把 JSON 拆成表是一次简单迁移，不构成技术债。

**为什么 `code` 需要唯一索引？** 唯一性是它存在的全部意义。所有行 `NULL` 时，MySQL 与 SQLite 都允许多个 `NULL` 共存，因此对**生产 0 行 / 历史无 code 行**零影响。

### 2.2 批量导入能力

#### 2.2.1 输入格式与列定义

支持 **TSV / CSV / Excel(xlsx)**，三种格式解析为同一张表：

| 列 | 必填 | 说明 |
|---|---|---|
| `subject` | 是 | 学科，如 `数据结构`。必须与 `path` 根节点一致（不一致 → error） |
| `path` | 是 | 归属路径，`>` 分隔，如 `数据结构>树>二叉树`。末节点即本行知识点，前面的节点自动匹配/创建 |
| `name` | 是 | 知识点名称，如 `二叉树` |
| `description` | 否 | 描述 |
| `difficulty` | 否 | `easy` / `medium` / `hard`，非法值 → error |
| `code` | 否 | 稳定编码，同批内与库内都不得重复 |
| `aliases` | 否 | 别名，`\|` 分隔，如 `堆栈\|stack` |

> 表头必须存在且顺序无关（按表头名定位列，不按列号），列名大小写不敏感，兼容中文表头（`学科/路径/名称/描述/难度/编码/别名`）。

Excel 解析：**建议引入 `openpyxl`（纯 Python，无编译依赖，`read_only=True` 流式读）**。理由：自主用 stdlib 解析 xlsx 需要处理 `sharedStrings` / `inlineStr` / 日期序列号，属重复造轮子。若不加该依赖，则 xlsx 返回 400 并提示「请在 Excel 中另存为 CSV/TSV」——**这是决策点 D1**。

#### 2.2.2 校验规则（error / warning 分级）

**error（阻断该行，`apply` 时若存在 error 则默认整批拒绝）**

| 编号 | 规则 |
|---|---|
| E1 | 缺少必填列 / 行缺 `subject`、`path` 或 `name` |
| E2 | `path` 末节点 ≠ `name` |
| E3 | `path` 根节点 ≠ `subject` |
| E4 | `difficulty` 不在 `easy/medium/hard` |
| E5 | `code` 格式非法（须匹配 `^[A-Za-z0-9][A-Za-z0-9._:-]{0,63}$`） |
| E6 | 批内 `code` 重复 / 与库内已有 `code` 冲突（指向不同知识点时） |
| E7 | 批内 `(normalized_subject, normalized_name)` 重复且内容不一致 |
| E8 | 构建完整父子树后产生**环**（含跨行环，见 §2.2.5） |
| E9 | 路径深度 > 8 层 |
| E10 | 行内有 `\t`/换行残留导致列数错乱（解析层拦截） |

**warning（不阻断，逐条列出）**

| 编号 | 规则 |
|---|---|
| W1 | 与库内知识点重名（将被跳过或按冲突策略处理） |
| W2 | `name` 命中库内其它知识点的 `aliases`（疑似同义，建议人工确认） |
| W3 | `aliases` 与库内已有名称/别名冲突 |
| W4 | 缺少 `description` |
| W5 | 缺少 `difficulty` / `estimated_minutes` |
| W6 | `path` 中间节点在库中不存在（将被自动创建，见 §2.2.4） |

#### 2.2.3 幂等与冲突策略

**幂等键 = `(normalized_subject, normalized_name)`**，即既有唯一约束。同一份文件重复导入**不会产生新增行**。

| 策略 | 行为 |
|---|---|
| `skip`（**默认，推荐**） | 已存在 → 完全跳过，不修改任何字段 |
| `update_empty` | 已存在 → **只填空字段，绝不覆盖已有非空值** |

> **明确不提供 `overwrite` 策略。** 批量导入直接覆盖人工维护的字段是数据事故的高发点；需要改单条请用管理页编辑。

`code` 若在库中已存在且指向同一知识点 → 视为同一行（跳过）。若指向不同知识点 → E6。

#### 2.2.4 父节点自动匹配

以 `path` 为准构造父子链（`数据结构 > 树 > 二叉树`）：

1. 逐级在库中按 `(normalized_subject, normalized_name)` 查找；
2. 命中 → 复用其 `id`；
3. 未命中 → **自动创建**（`source='import'`，`status='active'`，只填 `name/subject/parent_id`），并在报告的 `created_parents` 中逐条列出；
4. 自动创建的父节点**同属本次批次**（带 `import_batch_id`），回滚时一并撤回。

是否允许自动创建由参数 `auto_create_parent` 控制，**默认 `true`**（这是决策点 D3）。

> 与前置依赖的区别再次强调：`path` 表达的是**归属层级**，写 `parent_id`；**不写** `knowledge_point_prerequisites`。前置关系仍由大阶段 3 的前置编辑面板 / AI 提议维护。

#### 2.2.5 整批成环检测（关键）

逐行校验**查不出跨行环**：`A` 的行说父是 `B`，`B` 的行说父是 `C`，`C` 的行说父是 `A`——单看每一行都合法。

因此在 `preview` 阶段必须先**在内存中构建「库内已有点 + 本批新增点」的完整父子图**，再对整张图做环检测，命中则整批按 E8 拒绝并列出环路径。**这一步在写库前完成。**

#### 2.2.6 事务与回滚

| 层级 | 机制 |
|---|---|
| 单批执行 | `apply` 在**单个数据库事务**内完成，任一步失败即整体 `rollback`（天然满足「失败回滚」） |
| 事后撤销 | `POST /knowledge-import/batches/{id}/rollback`：删除该批**新建**且**仍未被引用、未被人工修改**的知识点；被引用（有题目关联/掌握度/前置边/子节点）或已修改的**跳过不删**并在报告中说明 |

批次记录 `knowledge_point_import_batches` 保存完整报告（`report_json`），因此「导入结果报告」可随时回看。

#### 2.2.7 规模与性能

- **单批上限 500 行**（超出直接 400），防止一次误操作写爆；
- 读取时**一次性预载**该学科全部知识点到内存（10²~10³ 规模 < 10ms），避免 N+1 查询；
- 写库使用 `bulk_save_objects` 分批（每 100 条一次 flush）但**共用同一事务**。

#### 2.2.8 流程

```
POST /knowledge-import/preview   ← 上传文件或粘贴文本
        │  仅解析 + 校验 + 整批成环检测 + 差异预演
        │  ★ 不写任何库
        ▼
   返回 {summary, rows[], errors[], warnings[], created_parents[]}
        │
        │  管理员在前端逐条看，确认
        ▼
POST /knowledge-import/apply     ← 同一份内容重新提交 + conflict_policy
        │  ★ 重新校验（防止 preview 与 apply 之间数据变化）
        │  ★ 存在 error 则默认拒绝，除非显式 force
        ▼
   写入（单事务）→ 落批次记录 → 返回报告
```

> **preview 不落库**：避免产生「预览到一半」的僵尸批次记录。批次记录只在 `apply` 时产生。

## 阶段二：AI 辅助题目知识点标注

### 2.1 数据模型：`knowledge_point_suggestions`（新表）

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | INT PK | |
| `question_id` | INT FK→`questions.id` `CASCADE`，索引 | 题目 |
| `knowledge_point_id` | INT FK→`knowledge_points.id` `RESTRICT`，索引 | 被建议的知识点 |
| `role` | `VARCHAR(16)` 默认 `primary` | 与 `question_knowledge_points.role` **同语义**，接受建议时直接透传，不引入第二套词汇 |
| `confidence` | `FLOAT` + `CHECK(0<=c<=1)` | LLM 置信度（决策点 D6：也可用 0~100 整数） |
| `reason` | `TEXT NULL` | 判定理由（管理员据此决策） |
| `status` | `VARCHAR(16)` 默认 `pending` | **`pending` / `accepted` / `rejected`**（严格按需求定义，不扩展） |
| `source` | `VARCHAR(16)` 默认 `ai` | `ai` / `rule`（纯关键词命中未走 LLM 时） |
| `model` | `VARCHAR(64) NULL` | 实际模型标识，用于识别离线兜底（见 R4） |
| `analysis_batch_id` | `VARCHAR(36) NULL`，索引 | 批量分析分组（UUID），用于「撤销某次批量分析」 |
| `reviewed_by_id` | INT FK→`users.id` `SET NULL` NULL | 审核人 |
| `reviewed_at` | DATETIME NULL | 审核时间 |
| `created_at` / `updated_at` | DATETIME | |

**约束与策略**

- `UNIQUE(question_id, knowledge_point_id)`——避免同一对建议堆积。
- **重跑策略（重要）**：
  - 已存在 `pending` → 更新 `confidence` / `reason` / `updated_at`（刷新，不新增行）；
  - 已存在 `rejected` → **保持 rejected，跳过**；
  - 已存在 `accepted` → **跳过**。
- **语义**：**管理员拒绝过的建议不会被 AI 反复翻案**。这是对人工决策的尊重，也让待办列表不会长期被噪声占满。（决策点 D7）

### 2.2 流程

```
题目（stem + options + analysis + subject）
   │
   ├─ ① 候选召回（规则，零 LLM 成本）
   │     词表 = 同 subject 且 status='active' 且 node_type='concept' 的知识点的 name + aliases + code
   │     对题干做关键词/别名命中 → 候选集合（目标 10~20 个）
   │     命中不足时按学科热度补齐至 CANDIDATE_MIN
   │     已存在正式关联的知识点 → 排除
   │
   ├─ ② LLM 精排（在候选内选择，不允许发明新知识点）
   │     输出 {candidates:[{knowledge_point_id, role, confidence, reason}]}
   │     后端校验：id 必须在候选集内 / 去重 / 条数上限 / 置信度区间
   │     ⚠️ 候选集只含 node_type='concept'，且接受时仍走
   │        QuestionKnowledgePointService（目录节点在服务层会被 NotLearnableNode 拒绝）
   │
   └─ ③ 落 knowledge_point_suggestions（status=pending）
              │
              │  ★ AI 到此为止，绝不触碰 question_knowledge_points
              ▼
       管理员在 /admin/question-labeling 查看
              │ 接受                    │ 拒绝
              ▼                          ▼
   调用既有 QuestionKnowledgePointService   仅更新 status=rejected
   （复用 primary 唯一性保证）→ 写正式关联
```

**关键复用点**：接受建议时**必须调用既有的 `QuestionKnowledgePointService` 写库**，而不是在标注模块里手写 INSERT。这样：
- 每题至多一个 `primary` 的既有保证继续生效；
- `UNIQUE(question_id, knowledge_point_id)` 冲突处理、`source` 标记（写 `source='ai'`）统一；
- **不产生第二套关联逻辑**，Phase 2 闭环零风险。

### 2.3 离线兜底防护（R4 的具体对策）

`AIModelGateway` 在无可用 Provider 时会走 `_offline_reply()` 返回模板文本。**批量标注必须显式拒收**：

1. 解析 `extract_json()` 失败 → 该题标记 `skipped`，**不落建议**；
2. 解析成功但 `knowledge_point_id` 不在候选集内 → 丢弃该条；
3. 每条建议记录 `model` 字段；离线兜底路径写入 `source='rule'` 或直接不入库并计入报告 `offline_rejected`。

> 宁可「这次没分析出结果」，也不允许模板文本变成一条待审核的假建议。

### 阶段二 API 变化

| 方法 | 路径 | 权限 | 说明 |

## 阶段三：知识质量保障

**只读**服务 `KnowledgeQualityService`，输出结构化报告，不修复、不写库。

### 3.1 知识点检查

| 编号 | 检查项 | 判定口径 | 级别 |
|---|---|---|---|
| K1 | 孤立知识点 | **仅针对 `node_type='concept'`**：既无父节点、也无子节点、且无前置边、且无题目关联 | warning |
| K2 | 无题目关联 | **仅针对 `node_type='concept'`**：`question_knowledge_points` 中无任何引用 | warning |
| K3 | 空描述 | `description IS NULL OR TRIM(description)=''` | info |
| K4 | 父子循环 | 沿 `parent_id` 上溯超过 N 层仍未到根，或回到自身 | **error** |
| K5 | 重复名称 | ① 同一 `normalized_name` 出现在多个 `subject`；② `name`/`aliases` 与实际存在的其它知识点名称/别名冲突 | **error** |
| K6 | 缺失难度/时长 | **仅针对 `node_type='concept'`**：`difficulty IS NULL` 或 `estimated_minutes IS NULL` | info |
| K7 | 悬空前置边 | 前置边的任一端指向 `status != 'active'` 的知识点 | warning |
| K8 | 目录结构质量 | **仅针对 `node_type='container'`** 的独立检查：空目录（无子节点）、目录被误关联题目 / 掌握度 / 前置边（历史脏数据） | warning |

> **口径说明 1**：K1「孤立」与 K2「无题目关联」是**两件事**——一个知识点可以是树中的中间层（有子节点、无题目），这不叫孤立。
>
> **口径说明 2（P0 node_type）**：K1 / K2 / K6 的分母**只统计 `node_type='concept'`**，目录节点（container）不参与「知识点数量」类指标；container 的正确性由 K8 的结构检查单独承担。凡本阶段后续出现的「知识点数量 / 覆盖率 / 关联率」等比例指标，分子与分母**默认都只取 concept**。

### 3.2 题目检查

| 编号 | 检查项 | 判定口径 | 级别 |
|---|---|---|---|
| Q1 | 无知识点题目 | `question_knowledge_points` 中无记录 | warning |
| Q2 | 多余关联 | ① 出现 **多个 `role='primary'`**（违反既有不变量）；② 关联数 > 5 | **error**（①）/ warning（②） |
| Q3 | 学科不一致 | `questions.subject` 与所关联 `knowledge_points.subject` 不匹配 | **error** |
| Q4 | 只有 secondary 没有 primary | 有 secondary 关联但无 primary | warning |

### 3.3 报告结构

```json
{
  "generated_at": "...",
  "scope": {"subject": "数据结构"},
  "summary": {"knowledge_points": 0, "questions": 8, "issues_total": 0, "errors": 0, "warnings": 0},
  "knowledge_points": {"K1": [...], "K2": [...], "..." : []},
  "questions": {"Q1": [...], "...": []},
  "health_score": 0
}
```

`health_score`：0~100 的简单加权（error 权重高、info 权重 0），供看板一句话展示。**纯统计量，不做预测。**

### 4.1 RecommendationContext

新增 `app/services/recommendation_context.py`：

```python
@dataclass(frozen=True)
class RecommendationContext:
    # ---- 用户侧 ----
    mastery: dict[int, int]              # knowledge_point_id -> 0~100
    weak_points: list[int]               # mastery < WEAK_THRESHOLD
    wrong_items: list[WrongItem]         # next_review_date / review_stage / mastered
    recent_answers: list[RecentAnswer]   # 最近 N 条（知识点、对错、时间）
    goal_tokens: frozenset[str]          # 来自用户目标 + 学习计划关键词
    # ---- 知识侧 ----
    prerequisites: dict[int, list[int]]  # 知识点 -> 前置列表
    unlock_counts: dict[int, int]        # 知识点 -> 解锁数（学完能解锁多少）
    difficulty: dict[int, str | None]
    estimated_minutes: dict[int, int | None]
    aliases: dict[int, tuple[str, ...]]
```

构造器 `build_context(db, user_id)`：**一次读取、内存复用**，避免既有引擎里的多次小查询。

### 4.2 规则版候选（按需求给的优先级）

| 优先级 | 候选来源 | 说明 |
|---|---|---|
| P1 | **当前薄弱知识点** | `mastery < 60`，按掌握度升序 |
| P2 | **即将复习知识点** | 错题本 `next_review_date <= today` 且未掌握 |
| P3 | **前置知识缺失点** | 目标知识点集合中，其前置未满足（`mastery < 70`）的知识点 |
| P4 | **高频错误知识点** | 最近 N 条作答中错误次数 ≥ 2 的知识点 |

## 7. 风险与缓解

| # | 风险 | 等级 | 缓解措施 |
|---|---|---|---|
| **R1** | 给已存在的 `knowledge_points` 加列，触发冻结契约 / drift 告警 | 中 | 生产该表 **0 行**（历史行也全为空），加列全部可空；严格走既有 5 步治理流程；历史 contract 逐字节不变（`_normalize` 已就绪） |
| **R2** | `UNIQUE(code)` 在 MySQL / SQLite 行为差异 | 低 | 两库均允许多个 `NULL` 并存；新增契约测试同时覆盖两库 profile |
| **R3** | xlsx 需新增 `openpyxl` 依赖，增加镜像构建时间 | 中 | 纯 Python 无编译依赖；若不接受则降级为「xlsx 提示另存为 CSV」（决策点 D1） |
| **R4** | **LLM 离线兜底把模板文本当结果**（既有 `_offline_reply`） | **高** | 三段防护：`extract_json` 失败即丢弃 / id 必须在候选集内 / `source`+`model` 留痕 + `offline_rejected` 计数 |
| **R5** | 批量导入误操作写坏数据 | 中 | preview 强制先看；`apply` 重新校验；单批上限 500；**单事务**；批次可回滚；冲突策略无 `overwrite` |
| **R6** | `preview` 与 `apply` 之间数据被改动（TOCTOU） | 低 | `apply` 阶段**重新执行全部校验**，出现新的 error 默认拒绝 |
| **R7** | 知识点难度影响掌握度算法，回归 Phase 2 闭环 | **高** | **明确禁止**：`difficulty` 字段**不参与** `MasteryService` 计算；掌握度仍取作答难度。既有掌握度测试必须全绿 |
| **R8** | 接受 AI 建议绕过 primary 唯一性保证 | **高** | 接受动作**只允许**调用既有 `QuestionKnowledgePointService`，模块内不得出现对 `question_knowledge_points` 的直接 INSERT |
| **R9** | 推荐 `today` 接口改动破坏前端 | 中 | 只追加可选字段，不删不改既有字段；既有前端 spec + 后端 30 项既有测试作为回归证据 |
| **R10** | `aliases` 用 JSON 列，无法 DB 层约束别名唯一 | 低 | 服务层校验 + §2.3 的 K5 质量检查兜底；文档写明 |
| **R11** | 被拒绝的建议永久不再提议，管理员困惑 | 低 | 前端在「已拒绝」页签显式说明；提供批量拒绝与按 `analysis_batch_id` 清理 |
| **R12** | 部署耗时长（依赖镜像慢，上轮约 35 分钟） | 中 | 预留发布窗口；部署期间保持只读观察，不重复触发 |

### 8.1 顺序（按依赖 + 「尽快可感知价值」排序）

```
M1 字段与迁移          ← 一切的地基，最小改动
```

## 10. 明确不做（本轮边界）

| 不做 | 原因 |
|---|---|
| 重构既有架构 / 移动模块 | 需求明确禁止 |
| 删除任何既有功能 | 需求明确禁止 |
| 修改历史 migration | 需求明确禁止 |
| 改动 `MasteryService` 算法 | 会破坏 Phase 2 闭环 |
| 改动 `PrerequisiteService` 算法 | 阶段 3 已验证，无需动 |
| 改动 `question_knowledge_points` 表结构 | 结构已完备 |
| 深度学习推荐 / BKT / GNN | 数据量差 3~5 个数量级，门禁未达 |
| BERT 微调 / 向量 kNN 标签传播 | 无已标注语料做冷启动 |
| 引入 Neo4j / Milvus | 10²~10³ 规模用邻接表 + 内存 BFS 足够 |
| 真正的 RAG（向量检索） | `documents=0`，无内容可检索；等教材到位 |
| 自动生成大量测试数据 | 需求明确禁止（会让指标失真） |
| 自动修改正式关联 / 自动接受 AI 建议 | 需求明确禁止 |
| 移动端重构、大规模 UI 改版 | 不在本阶段范围 |
