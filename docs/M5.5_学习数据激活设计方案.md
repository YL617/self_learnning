## 0. 结论摘要

**一句话诊断**：系统「有推荐逻辑，但没有真实反馈数据」，根因是链路断在 **「题库 → 用户」**，
且这不是一个字段问题，而是 **三层缺口**：**① 无供给管道　② 无审核门禁　③ 无用户可见入口**。

**关键因果链**

```
questions = 8（全部 visibility=private，owner=uid1 管理员，source=ai）
  → list_question_bank() 恒空（0 条 shared）
  → 前端 questionsApi.questionBank() 无任何视图调用（后端有端点、无消费者）
  → 非管理员：既看不到、也答不了（_resolve_answerable_question 只认 owner/admin/shared）
  → answer_records 只能由管理员产生（现存 4 条历史）
  → user_knowledge_point_mastery = 0
  → 推荐 review_weak / practice 候选恒空；学习路径 step.satisfied 恒 False
  → 「个性化」在产品上无从体现
```

**三个必须做**

1. 给题目加**审核态**（`review_status`），并把「对他人可见」定义为 `approved ∧ shared`（Q1=B 已锁定）。
2. 建**供给管道**：AI 生成 + xlsx/CSV 批量导入，产物一律先落 `draft`。
3. 补**用户可见入口**：前端消费 `/question-bank`（当前后端有、前端无）。

**三个坚决不做**

1. 不改 mastery / prerequisite / recommendation **算法**（本轮数据问题≠算法问题）。
2. 不引入 **BKT / DeepKT**、不做复杂多角色权限平台、**不实现 QTI 全套**（只借信息模型）。
3. **不一次性灌 100 题**——先 20 题把「生成→审核→发布→作答→mastery」流程跑通，再放量。

**工作量总览**：约 **5.5 ~ 8 人日**（代码 3~4 / 内容 2~3 / 审核 0.5~1）。详见 §8。

- **无题库批量导入**——但 `knowledge_import.py` 已实现 **xlsx/CSV/TSV 解析 + 校验 + preview + 批次 + 回滚**（用于知识点），且 `requirements.txt` **已含 `openpyxl>=3.1.0`** 与 `python-multipart`（文件上传现成）。→ 题目导入**有现成范式可复刻**，无需新增依赖。

| # | 缺口 | 证据 |

## 2. 题库生命周期设计（状态机）

### 2.1 建模方式选型（B1 vs B2）

| 方案 | 做法 | 影响面 | 判定 |
|---|---|---|---|
| **B1 双轴（推荐）** | `visibility`（可见范围：private/shared）**不动** + **新增** `review_status`（生命周期） | 纯新增列；现有全部 `visibility` 查询**零改动** | ✅ **采用** |
| B2 单轴 | 用 `status` 取代 `visibility` | 触发 `ck_questions_visibility` + `list_question_bank` + `_resolve_answerable_question` + qkp service + AdminQuestionCreate 等**多调用点**与 CHECK 约束的连锁改动 | ❌ 回归风险高，否决 |

> 采纳理由：`visibility` 是**承载语义**字段（3+ 处查询依赖它），改成单轴会扩散回归面；新增一列是**追加式**改动，与既有「最小必要改动」纪律一致。

### 2.2 状态机（`review_status`）

```
        ┌──────────────────────────────────────────────────────────┐
        │                                                          │
     [draft] ──submit_review──▶ [pending] ──approve──▶ [approved] ──publish──▶ (shared)
        ▲                          │                       │
        │                       reject                  archive
        │                          ▼                       ▼
        └────── edit ────────  [rejected]             [archived]
```

- 用户 Q1 锁定的 5 态 `draft→pending→approved→shared→archived`，在本模型里 **`shared` = `(approved ∧ visibility='shared')`**（"已发布"）。
- **对外可见的充要条件**：`visibility='shared' AND review_status='approved'`。
- 其余状态一律不进共享池。

### 2.3 状态转移规则

| 状态 | 含义 | 可执行动作 | 执行者 |
|---|---|---|---|
| `draft` | 草稿（AI 生成 / 手建 / 导入的初始态） | `submit_review` / 编辑 / 删除 | owner / 管理员 |
| `pending` | 待审 | `approve` / `reject` | 管理员 |
| `approved` | 已过审（尚未发布） | `publish`（→ shared）/ `archive` | 管理员 |
| `rejected` | 退回 | 编辑后重新 `submit_review` / 删除 | owner / 管理员 |
| `archived` | 归档 | 只读（保留追溯，不再进入池） | 管理员 |

> 存量 8 题：`visibility=private` → 无论 `review_status` 取值都**不对他人可见**，故新增列默认值对存量行为**零影响**。建议列默认 `draft`。

## 3. 数据库影响分析

### 3.1 结论：**需要 1 个 migration（新增列）**

| 变更 | 内容 | 是否必需 |
|---|---|---|
| **M-A** | `questions` 新增 `review_status VARCHAR(16) NOT NULL server_default 'draft'` + `CHECK review_status IN ('draft','pending','approved','rejected','archived')` | ✅ 必需（Q1=B 的直接落地） |
| **M-B** | `questions` 新增审核留痕：`reviewed_by`(FK users, nullable) / `reviewed_at`(nullable) / `review_note`(nullable) | ⭕ 建议（可追溯、可审计；成本低） |
| **M-C** | 新增 `question_import_batches` 表（对齐 `knowledge_point_import_batches`：谁/何时/格式/策略/计数/status/回滚） | ⭕ 视导入方案（若要批次回滚则必需） |
| **M-D** | `questions.import_batch_id`(FK → batches, nullable) | ⭕ 与 M-C 成对 |

> 本报告**建议先落 M-A（+M-B）**，M-C/M-D 待「导入方案」定稿再决定——避免为尚未确定的批量能力过早建表。

### 3.2 时机判断（关键）

**`questions` 当前仅 8 行、且 `visibility='shared'` 行数 = 0。这是改结构成本最低的窗口。**
一旦灌入 50~100 题，再加列就要面对**回填 + 引用修复 + 冻结合同重算**。→ **先改结构、后灌数据**。

### 3.3 Schema 治理链路（5 处同步点，必守）

新增 revision 必须同步：
1. `app/models/learning.py`（`Question` 加列 + CHECK）
2. `app/models/__init__.py`（若有新表）
3. `app/core/adoption_inspector.py` 的 `TARGET`
4. `app/core/schema_reconciliation_manifest.py`
5. `tests/freeze_schema_profiles.py` 的 `REVISIONS` + `RELEASE_HISTORY`

收尾必跑：`ruff check app tests` → 目标测试 → `alembic upgrade/downgrade/upgrade` → `alembic check` → `alembic heads` → 容器内 `verify_schema_runtime.py`。
注意：**加列属于「结构变更」**（不是合同中性 revision），冻结合同哈希会真实变化——`RELEASE_HISTORY` **追加新版本**，历史版本字节不变。

### 3.4 兼容性与回滚

- 新增列带 `server_default` → **旧代码可继续运行**（读不到新列不报错）；本变更**向后兼容**。
- 回滚：`alembic downgrade` 删列；数据无损（列外信息不动）。

| 方法 | 路径 | 作用 | 说明 |

## 5. AI 出题流水线

```
[需求]  学科 + concept(knowledge_point_id) + 难度 + 数量
   │
   ▼
[生成]  generate_questions()  ← 复用现有（AIModelGateway.generate_json）
   │      · 若 documents>0 可注入教材 chunk 作 grounding（当前 0 → 无 grounding）
   ▼
[结构校验]  ★ 显式拒绝离线/空结果
   │      · generate_json 失败 → {} → generate_questions 抛 RuntimeError
   │      · 必须校验：stem/answer 非空、choice 选项 ≥2、answer 与选项可对齐
   ▼
[语义自检]（新增，轻量）
   │      · 解析长度阈值（**在 _ensure_analysis 补全之前**统计原始长度）
   │      · 答案 ↔ 解析一致性（可选 LLM judge，标注不确定项）
   ▼
[知识点绑定]  attach(role='primary', source=QKP_SOURCE_AI)   ← 走既有服务关口
   │      · concept-only（container 一律拒绝）/ 学科一致 / primary 唯一 / 幂等
   ▼
[落库 draft]  Question(review_status='draft', visibility='private' 待审)
   ▼
[人工审核]  approve / reject（最低门槛：答案对？解析对？知识点对？难度合理？）
   ▼
[publish]  → visibility='shared' + review_status='approved'
```

**硬约束（来自既有设计）**

1. **离线兜底必须显式拒绝**：`AIModelGateway` 有两条静默降级路径（无 `api_key` / 请求异常）都会返回模板文本；`extract_json` 失败 → `{}`。批量流水线**必须保留原文判定**，不得把「0 题」当正常结果静默跳过。
2. **绑定只能走 `attach()`**，禁止手写 INSERT（否则绕过 concept 关口与学科一致校验）。
3. **`_ensure_analysis` 会在补全前污染「解析长度」信号** → 质量门禁须读取**原始** `analysis`。
4. **grounding 缺口是内容前置**：`documents=0` 时生成仅依赖系统提示词 + 知识点名，质量下限更低 → 首批更依赖人工审核兜底。

## 6. 首批题库目标

| 批次 | 题量 | 累计 | 覆盖 concept（累计） | 目的 |
|---|---|---|---|---|
| **批 1（试点）** | 20 | 20 | ~12 | **跑通全流程**：生成→审核→发布→用户作答→mastery 写入 |
| 批 2 | 15 | 35 | ~20 | 补齐高频章节 concept |
| 批 3 | 15 | **50** | **20~30** | 达到首期目标 |

**覆盖优先策略**：优先覆盖 (a) 50 条前置边的端点 concept、(b) 核心章节（线性表/树/图/排序/栈队列）的原子 concept、(c) 已有 mastery 缺口的 concept。每题 **1 个 primary concept**（沿用 M5 Step5 规则，不引入 secondary）。

**难度/题型分布（建议）**：`easy:medium:hard ≈ 3:5:2`；题型以 `choice` 为主，逐步引入 `fill`。

**验收判据（批 1 完成即验证）**

- 题库：`questions` 中 `visibility='shared' ∧ review_status='approved'` ≥ 20；覆盖 concept ≥ 12。
- 闭环：真实用户（非 admin）作答 → `user_knowledge_point_mastery` **从 0 变为非 0**（这是 M5.5 的核心成败标志）。
- 推荐：`/recommendations/today` 出现 `review_weak`/`practice` 类候选。
- 前端：非 admin 用户可在界面看到并作答共享题。

## 7. 开源与标准调研（七问）

### 7.1 QTI 3.0（1EdTech 题库互操作标准）

① 解决「题库/试卷跨系统交换」；② 输入=XML 内容包；③ 输出=`assessmentItem`（单题）/`assessmentTest`（试卷）/结果报告；④ 无需数据即可用；⑤ **信息模型高度相关**（`responseDeclaration`=正确答案、`outcomeDeclaration`=评分变量、`itemBody`=展示、`responseProcessing`=判分、**元数据含难度/曝光度等统计**）；⑥ 全套实现成本极高（XML + 内容包 + 30+ 交互类型）；⑦ 可引入信息模型，不引入实现。
→ **采纳**：`assessmentItem`↔`questions`、`responseDeclaration`↔`answer`、`responseProcessing`↔`check_answer`、item **统计元数据**（难度/曝光）↔ 未来 `difficulty`/使用统计。**不引入 XML / 内容包**。

### 7.2 AIG 与「Item Factory」范式（Duolingo Item Factory + AQuAP）

① 解决「大规模高质量出题」；② 输入=专家蓝图/任务族；③ 输出=候选题目池；④ 需要**数据与专家**；⑤ **高度相关**；⑥ 可直接借流程；⑦ 能引入流程、不能引入规模。
→ **采纳其流程**：`SME 蓝图 → AI 生成 → 自动筛查（长度/语法/格式/基本效度） → 人工质量评审 + 公平性评审 → 试测 → 上线`。**核心洞见**：「**流利度易自动化，效度不能**」→ 人工评审不可省。另借「**有效题库规模 / 曝光度**」概念，用于后续题库健康度。

### 7.3 HITL（Human-in-the-Loop）验证

① 解决「自动化产物的可信度」；② 输入=机器产物 + 置信度；③ 输出=自动通过 / 转人工；④ 无需训练；⑤ **直接可用**；⑥ 低成本；⑦ 可直接引入。
→ **采纳**：**置信度阈值 + 确定性阻断规则 + 转人工队列**。落到本项目 = 「自动筛查（结构/长度）→ 人工审核队列（approve/reject）」。

### 7.4 与既有标准的关系

- **1EdTech CASE**：已在知识点侧借用（稳定编码 / 别名 / 版本），题库侧**延续同一策略**（`knowledge_point_id` 即稳定锚点）。
- **Moodle `tool_lpimportcsv` / GIFT/Aiken**：题目导入格式的工程参考——**本项目用 xlsx/CSV**（`openpyxl` 已装），无需引入其格式。

### 7.5 三条可直接落地的结论

1. **审核态是行业标准做法**（QTI item 元数据、AIG 人工评审、HITL 均要求发布前状态），Q1=B 有外部背书。
2. **自动筛查 + 人工评审两段式**是 AIG/HITL 的共识 → 直接作为 §5 流水线骨架。
3. **不实现 QTI**：只借信息模型；避免为「标准合规」引入远超当前规模的复杂度。
