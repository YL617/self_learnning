## 第一部分：M5 产品目标重新定义

### 1.1 最终用户体验（用户视角，一屏可答五问）

用户登录后打开 `/my-plan`（我的学习计划），应能依次得到：

| # | 用户的问题 | 页面给出的答案 | 数据来源（已有 API） |
|---|---|---|---|
| 1 | 我现在学得怎么样？ | 学习进度卡片：已学知识点 / 总概念数、平均掌握度、今日待复习 | `GET /mastery/summary` + `GET /knowledge-points?node_type=concept` |
| 2 | 我哪里薄弱？ | 薄弱知识点列表（掌握度 < 60），含掌握度条 | `GET /mastery/weak` |
| 3 | 我下一步学什么？ | 今日推荐列表（按 `order` 排序，1..N） | `GET /recommendations/today?limit=10` |
| 4 | 为什么推荐这个？ | 每条推荐展示「推荐理由」原文 + 「打分依据」分解 + 人话化标签（正确率 / 前置依赖 / 未复习天数） | 复用 `reason` + `components`；正确率由 `GET /mastery/{kp_id}` 派生（前端计算） |
| 5 | 我该怎么走完？ | 学习路径时间线（前置 → 当前 → 后续），并可一键"开始学习"直达该知识点的练习 | `GET /knowledge-points/{id}/path` + `question_ids` |

### 1.2 设计原则

- **稳定可用 MVP 优先**：不追求复杂 AI 算法，做"确定性、可解释、可核对"的学习助手。
- **复用优先**：所有数值来自既有服务，不引入第二套"今天干什么"的计算逻辑。
- **只读优先**：推荐链路保持纯只读，不自动落 `PlanItem`（避免与既有学习计划冲突，沿用 `recommendation.py` 模块头注释的既定设计）。
- **零 schema 变更**：不新增表/列/约束。

### 1.3 明确不做（产品层面）

不做"AI 自动排课/自动代理规划"，不做"生成式推荐理由"（LLM 实时参与数值），不做"社交/排行榜"。理由：数据规模未达 V2 门禁，且违反最小改动原则。

#### P0-2 学习路径可视化

- **形态**：新增组件 `LearningPathTimeline.vue`（竖向时间线）
  ```
  基础概念（前置，已满足 ✓）
        ↓
  前置知识（前置，未满足 ✗）
        ↓
  当前学习点（is_target，高亮）
        ↓
  后续能力（解锁的下游）
  ```
- **数据**：`GET /knowledge-points/{id}/path` → `steps[]`（每步含 `order / knowledge_point / mastery_score / satisfied / is_target`）
- **复用**：已有 `knowledgePointsApi.learningPath(kpId)` 前端方法与 `LearningPath` TS 类型
- **落点**：`/my-plan` 页内嵌 + 知识图谱页可选入口（二选一，见决策点 3）
- **不改后端**：`/path` API 与 `LearningPathOut` schema 一律不动

#### P0-3 推荐解释增强（**纯前端**）

要求把"推荐：二叉搜索树"升级为可理解的解释：

```
推荐：二叉搜索树
推荐原因：
  · 你的相关题目正确率 45%（低于薄弱线 60%）
  · 它是后续「AVL 树」的前置知识（解锁 3 个下游知识点）
  · 最近 7 天未复习
  · 打分依据：动作基础分 ×52、掌握度缺口 ×1.33、解锁加成 ×1.24、最近练习折减 ×1.00
```

- **实现方式（不改后端文案）**：
  - `reason` / `components` **直接展示**（已下发）
  - "正确率 %" 由前端按需调用 `GET /mastery/{kp_id}` 取 `correct_count / attempt_count` 计算
  - "最近 N 天未复习" 由 `last_answered_at` / `last_reviewed_at` 前端计算
  - "解锁 N 个下游" 取 `components.unlock` 反推（`1 + 0.12×N`）
- **为什么放前端**：后端 `reason` 文案被 `tests/test_recommendation_service.py`（29 项）断言覆盖，改文案会破坏"保持已有测试稳定"原则；前端渲染是纯增量、零回归面。

#### P0-4 推荐 → 开始学习闭环（G5）

- 现状：`DashboardView.onStartRecommendation` 只做 `router.push('/wrong-book' | '/questions')`，`question_ids` 已下发但**未使用**
- **设计**：`RecommendationCard` 的 `start` 事件携带 `item`；`/my-plan` 页把 `knowledge_point_id` 作为 `route.query` 传给练习题页
- **配套（向后兼容小改）**：`QuestionsView.vue` 读取 `route.query.knowledge_point_id` 预填筛选条件（**不传 query 时行为完全不变** → 既有 `QuestionsView.spec.ts` 不受影响）
- **风险等级**：低（追加式，不改变默认路径）

## 第六部分：推荐系统产品化优化（**不改算法**）

### 6.1 现象

```
GET /api/v1/recommendations/today?limit=5 （生产只读实测 2026-10-11）
  items: 5 —— 全部 learn_new，score 全部 84.5，reason 全部"没有前置知识点，可以直接开始…"
  /mastery/summary → {"total":0,"weak_count":0,"average_score":0.0,...}
```

### 6.2 定性：**这是数据问题，不是算法问题**

| 因子 | 公式项 | 生产真实取值 | 是否退化 |
|---|---|---|---|
| `urgency` | 错题逾期加成 | 错题 0 条 → 无 `review_wrong` 候选 | 无候选，非退化 |
| `gap` | `1 + 0.6×(100-score)/100` | 所有 `learn_new` 用 `MASTERY_INITIAL` 常量 → **同为 1.3** | ✅ **退化（因 mastery=0）** |
| `unlock` | `1 + 0.12×解锁数` | 前置边 0 条 → `unlock_count` 恒 0 → **同 ×1.0** | ✅ **退化（因 prerequisite=0）** |
| `goal` | 命中目标 ×1.25 | 多数概念命中同一目标 → **同 ×1.25** | ✅ **部分退化** |
| `recency` | 最近 3 天练过 ×0.6 | 无作答记录 → 恒 ×1.0 | ✅ 退化（因无答题） |

**结论**：算法本身正确且可解释；`score` 相同是因为**所有区分度因子所需的数据都为 0**。因此**绝不能改算法**——改算法只会掩盖数据缺失，且违反红线。

### 6.3 最低成本解决方案（按投入产出排序）

| 优先级 | 措施 | 成本 | 收益 | 是否本次可做 |
|---|---|---|---|---|
| ① | **前置关系种子数据**（让 `unlock_count` 与硬前置生效） | 数据工作，0 代码 | 直接让 `unlock` 因子分化 → 排序立刻有区分度 | ✅ 本阶段（第七部分） |
| ② | **用户答题数据积累**（真实作答产生 mastery） | 运营，0 代码 | 让 `gap`/`recency`/`review_weak`/`review_wrong` 生效 | ⏳ 运营持续 |
| ③ | **推荐解释**（把"为什么"讲清楚） | 前端，1 组件 | 即使同分，用户也能理解推荐依据 | ✅ P0-3 |
| ④ | 目标/学科权重细化 | 改 `goal` 因子 | 中 | ❌ 触碰算法，不做 |

> **本阶段只做 ①（数据）+ ③（解释）**，② 由运营自然积累，④ 明确不做。

### 6.4 观察指标（用于验证"不再退化"）

- 补种子后：`/recommendations/today` 的 `score` **不再全部相同**，且 `components.unlock` 出现 >1.0
- 有真实作答后：`review_weak`/`review_wrong` 动作出现，`components.gap`/`recency` 发生变化

## 第七部分：前置关系数据方案（A→B 如何进入系统）

### 7.1 目标

为 56 个 concept 建立高置信前置边，使 `A → B`（先学 A 才能学 B）进入 `knowledge_point_prerequisites`，从而激活推荐的 `unlock` 因子与硬前置阻塞。

### 7.2 三方案比较

| 维度 | 方案 A：管理员人工维护 | 方案 B：LLM 辅助生成 + 人工审核 | 方案 C：完全自动生成 |
|---|---|---|---|
| 流程 | 管理员在管理端逐条 `POST /prerequisites` | `POST /prerequisites/suggest`（LLM 只提议）→ 管理员逐条确认落库 | 批量脚本直接 `INSERT` |
| 准确性 | **最高**（逐条人工判断） | **高**（LLM 提议 + 人工把关，MoocRadar 范式） | 低（无把关，易引入错误前置，污染学习路径） |
| 成本 | 高（56 节点 × 人工梳理，易漏） | 中（LLM 提议后人工快速确认/剔除） | 最低 |
| 可维护性 | 中（新增知识点需人工补） | **高**（新增知识点可再跑一次 suggest） | 低（错误难以发现） |
| 现有支持 | ✅ 写接口已有 | ✅ **端点 + 服务已存在**（`prerequisite_suggest.py`，只提议不落库；候选仅 concept，排除成环） | ⚠️ 有写接口但无审核链路 |
| 风险 | 漏建、覆盖不全 | LLM 幻觉（由人工审核拦截） | **污染生产学习路径**，且绕过治理 |

### 7.3 推荐方案：**B（LLM 辅助 + 人工审核）**，并以 A 作为兜底

推荐理由：
1. **端点已存在**：`POST /knowledge-points/{id}/prerequisites/suggest` 已实现"只提议、不落库"，候选装载已过滤 container（`prerequisite_suggest.py` 候选仅 `node_type=concept`），与 M4 红线天然一致。
2. **权责清晰**：数值与写入权留给人，模型只提供候选与理由 → 符合项目"LLM 不掌数值"的既定纪律。
3. **成本可控**：56 个 concept 可分为"数据结构 V1.2 同章节"先跑，人工快速确认。
4. **可维护**：新增知识点可重复执行。

**执行方式（属于数据工作，不是代码工作）**：
- Step D1：管理员在管理端对每个 concept 触发 `suggest`，得到候选 + 置信度 + 理由
- Step D2：**人工逐条语义审核**（沿用 alias 质量 G6 的"逐节点人工语义判断"标准），确认 `strength`（硬前置建议 100，软建议 <60）与方向
- Step D3：确认后才 `POST /prerequisites` 落库（**需你另行批准后执行，本次不执行**）
- Step D4：只读复核——`GET /knowledge-points/{id}/path` 与 `/recommendations/today` 观察分化

> ⚠️ **本次不执行任何写库**。本部分仅给方案与流程；落库需你显式批准，并遵守"先列清单 → 人工确认 → 小批量执行"的既有纪律。

### 7.4 兜底：方案 A 的种子清单

若 LLM 提议质量不达预期，可退回方案 A：由你/我基于 `数据结构知识库V1.2.csv` 的章节归属与难度层级，整理一份**候选前置清单（仅清单，不落库）**供人工审核。是否要产出该清单见决策点 4。
