**pyBKT 关键情报**（来自官方 README 与 EDM 2021 论文）：

- 纯概率模型（HMM），参数只有 4 个/知识点：`prior`(L0)、`learn`(T)、`guess`(G)、`slip`(S)，用 EM 拟合。
- **支持变体**：个体先验/学习率/guess/slip、逐题 guess/slip（KT-IDEM）、逐资源学习率。
- **有纯 Python 与 C++ 两种后端**；官方性能表：合成数据 500 学生拟合 — 纯 Python **1分55秒**，C++ **1.5 秒**；5000 学生 — 1小时30分 vs 45 秒。
- ⚠️ **Windows 只提供纯 Python 版**（README 明确写 "for Windows, we only offer the slower, pure Python version"）。我们的开发机是 Windows，服务器是 Linux → 本地慢、生产快，可接受。
- 输入是 DataFrame/CSV：`user_id / skill_name / correct / order_id`。
- 输出：`predict()` 给每个作答点的**掌握概率**（0~1），以及拟合后的参数表。

**pyKT 关键情报**：Torch 实现，覆盖 DKT / DKT+ / DKVMN / SAKT / SAINT / AKT / GKT / LPKT / IEKT / DIMKT 等 10+ 模型，7 个标准数据集（assist2009/2012/2015/2017、ednet、edi2020、SLP）。**注意**：它的数据集规模是百万级交互，仓库里带的是**数据预处理管线**而不是可直接用的小样本训练能力。

**PyEdmine 关键情报**：v1.0.0（2025-08-15）LTS，实现了 **28 个 KT 模型 + 7 个认知诊断 + 3 个习题推荐 + 4 个学习路径推荐**，统一数据格式，支持 14 个数据集。依赖 `pandas/numpy/sklearn/torch`。这是「四个任务的模型动物园」，适合**读它的 LPR 实现来学思路**，不适合直接当服务依赖（Torch + 大数据的体积与风险）。

### C. Learning Path Recommendation

文献中的主流做法有两类：

1. **基于知识图谱/前置关系的路径规划**（prerequisite graph + 拓扑排序 / 图搜索 / 强化学习）
2. **基于序列建模的路径推荐**（把路径当序列，用 RL 或 seq2seq）

参考数据与基石：

| 资源 | 规模 | 说明 |
|---|---|---|
| **MoocRadar** (`THU-KEG/MOOC-Radar`) | 2,513 题 / **5,600 细粒度概念** / 14,224 学生 / **1200 万+ 行为记录** | SIGIR 2023，带 Bloom 认知标注 + 习题图 + 前置概念关系；概念密度 2.228 概念/题 |
| ASSISTments 2009 | 平均序列长 82.2，概念密度 **0.004** | 经典但概念粒度极粗 |
| EdNet-KT | 平均序列长 121.5，概念密度 0.014 | 韩国 AI 教辅，百万级 |
| PyEdmine 内置 14 数据集 | — | 统一格式，含学习路径推荐任务 |

**关键结论**：C 方向我们**不需要外部数据**。因为：

- 「树依赖链表」这种**前置关系是学科固有知识**，不是从数据里学出来的统计规律；
- 我们的 `knowledge_points` 已经有 `parent_id`（**层级/归属树**），但**没有前置依赖 DAG** —— 这是本阶段最重要的一个缺口（详见 §3.3）；
- 一旦有了前置边，路径规划就是**带条件过滤的 DAG 遍历**，纯确定性、零训练、可解释、可测试。

MoocRadar 的价值在于：它给了我们**「从哪里获得前置关系」的工程范式** —— 论文用的是「LLM 自动抽取 + 40 位专家标注修正」的混合流水线。这个范式可以直接搬到我们的管理后台。

### E. AI Tutor / RAG

前沿论文（可作为 V3 的立论依据，但都是**方法参考**而非代码）：

| 论文 | 会议 | 核心思路 |
|---|---|---|
| **LLMKT** — Exploring Knowledge Tracing in Tutor-Student Dialogues using LLMs | LAK 2025 | 用 LLM 抽取对话中的知识点 + 判定学生是否答对，再在该标注数据上做 KT；LLM 只做**标注**，不做数值建模 |
| **CIKT** — Collaborative and Iterative Knowledge Tracing | EMNLP 2025 | 双组件：**Analyst**（从历史作答生成可解释的用户画像）+ **Predictor**（用画像预测表现），二者迭代互训 |
| **NTKT** — Next Token Knowledge Tracing | arXiv 2025-11 | 把 KT 重构成 next-token 预测，用预训练 LLM 表示学生历史与题目文本；对**冷启动（新题/新用户）泛化更好** |
| CEKT — Enhancing programming KT with LLMs | KBS 2025 | 用 prompt tuning 让 LLM 构建 Q 矩阵与知识点关系图（**正是我们「LLM 提议前置关系」的学术依据**） |

**共同范式**：**LLM 负责「理解与解释」，统计模型负责「数值」。** 这与我方大阶段 2 已确立的「掌握度数值必须确定性、禁止 AI 决定」完全一致，可以直接继承。

## 2. Step 2：候选方案七问分析

### 2.1 pyBKT（Bayesian Knowledge Tracing）

| 问题 | 回答 |
|---|---|
| **1. 解决什么问题** | 在**单个知识点**维度上追踪学生「是否已掌握」的隐藏状态，输出逐步更新的掌握概率 |
| **2. 输入** | 长表：`user_id, skill_name, correct(0/1), order_id`（可选其他 features）。**每次作答一行** |
| **3. 输出** | ① `predict()` → 每个作答点的掌握概率 P(mastered)；② 拟合参数 `prior/learn/guess/slip`（每个 skill 一组） |
| **4. 需要多少数据** | **这是关键**。BKT 参数是 per-skill 的 4 个标量，用 EM 拟合，**远低于深度学习**。经验下限：**单知识点 30~100 次作答**能拟合出非退化的参数；< 20 次会退化成先验。官方 benchmark 用的是 500~5000 学生，但那是为了**跨学生共享参数**（个体化变体）。对**冷启动单用户**，可以退化为「先验为主 + 少量更新」 |
| **5. 适合我们吗** | **部分适合**。它的模型假设（掌握是二值隐状态 + 学习转移 + 猜测/失误）比我们的规则式加减分更「认知科学」。但**真正的问题是共享参数从哪来** —— 我们只有 1 个用户，无法为每个知识点拟合出可靠参数 |
| **6. 改造成本** | 中。需要：加 `pyBKT` 依赖（含 C++ 编译，Windows 只有纯 Python）→ 从 `answer_records` 导出长表 → 拟合/预测 → 把概率写回。**风险**：纯 Python 版在 Windows 上慢；EM 在小样本上可能不收敛；`pyBKT` 是研究库，不是服务化组件 |
| **7. 可直接引入吗** | **现阶段不建议**。建议**先自研一个 BKT 的极简版（几十行，闭式更新，无需 EM）**，等价于「带学习率与猜测率的贝叶斯更新」，作为掌握度的**第二路信号**，与现有规则式算法做 A/B。等用户量起来、确认收益后再决定是否引入 `pyBKT` 做参数拟合 |

### 2.2 pyKT / EduKTM / PyEdmine（深度 KT）

| 问题 | 回答 |
|---|---|
| **1. 解决什么问题** | 用神经网络建模学生作答序列，预测下一次作答正确率 |
| **2. 输入** | 序列 `(question_id, concept_id, correct)`，通常还有 timestamp、response time |
| **3. 输出** | 下一题答对的概率；AKT 等模型还能给出**题目-概念的注意力权重**（可解释性来源） |
| **4. 需要多少数据** | **10⁶ 交互起步**。参考标准：ASSISTments2009 约 34 万次作答、MoocRadar 1200 万行为记录、EdNet 千万级。DKT 类模型参数量 10⁵~10⁷，**在小数据上必然过拟合到「记住训练集」** |
| **5. 适合我们吗** | ❌ 不适合。**当前只有 4 条作答记录**，差 **6 个数量级** |
| **6. 改造成本** | 高：Torch 依赖（镜像体积、CPU 推理、训练环境）、数据管线、模型版本管理、CI 时间 |
| **7. 可直接引入吗** | ❌ 禁止。**并且要写进门禁**：数据量未达阈值前，任何人不得引入 |

### 2.3 RecBole / LightGCN（通用推荐）

| 问题 | 回答 |
|---|---|
| **1. 解决什么问题** | 从大规模用户-物品交互中学习偏好，做 Top-N 推荐 |
| **2. 输入** | `.inter` 交互文件：`user_id, item_id, rating/timestamp` |
| **3. 输出** | 每个用户的 Top-N 物品列表 + 打分 |
| **4. 需要多少数据** | 协同过滤的本质是**「相似用户」**。用户数 < 100 时，任何 CF 模型都不如「按知识点难度排序」的启发式 |
| **5. 适合我们吗** | ❌ 我们现在是**单用户系统**。CF 完全无法工作 |
| **6. 改造成本** | 高（Torch + 数据集转换 + 离线训练流水线），收益在数据量达标前为 **0** |
| **7. 可直接引入吗** | ❌ 现阶段禁止。留到「用户量 ≥ 10³」时重新评估 |

### 2.4 py-fsrs（FSRS 间隔重复）

| 问题 | 回答 |
|---|---|
| **1. 解决什么问题** | 用记忆强度模型（DSR: Difficulty-Stability-Retrievability）决定「下次什么时候复习」 |
| **2. 输入** | `Card`（状态 + 到期时间 + 稳定度 + 难度）+ `Rating`（Again/Hard/Good/Easy） |
| **3. 输出** | 更新后的 Card（新到期时间、新的 scheduled_days）+ ReviewLog |
| **4. 需要多少数据** | **默认参数无需训练**（19 个权重有官方默认值 + 全局优化器可选）。这是它最大的价值：**开箱即用，零数据门槛** |
| **5. 适合我们吗** | **很适合**。它正好替换我们大阶段 2 的固定间隔表 `{1:1, 2:3, 3:7, 4:15, 5:30}` —— 固定间隔是 Ebbinghaus 的简化版，FSRS 是它的现代替代，且**同样是确定性的纯函数**（符合「禁止 AI 决定数值」） |
| **6. 改造成本** | **低**。纯 Python（无 torch/C++），MIT，有 pytest + mypy + ruff CI，有 `to_dict/from_dict` 可直接序列化到我们的字段。只需把 `rating` 从我们的 `correct: bool` + `spent_seconds` + `attempt_count` 映射过去 |
| **7. 可直接引入吗** | ✅ **可以，建议引入**（作为 V1 的一部分，或独立小阶段）。但注意：引入会**改变现有错题复习排期语义**，需要 migration + 旧数据迁移策略 + 回归测试 |

### 2.5 自研「规则 + 图」学习路径推荐

| 问题 | 回答 |
|---|---|
| **1. 解决什么问题** | 「下一步学什么」「为什么」「什么顺序」—— 在**没有足够行为数据**时唯一可靠的路径规划方式 |
| **2. 输入** | ① 前置关系 DAG（知识点边）；② 用户掌握度 `user_knowledge_point_mastery`；③ 错题/复习队列；④ 用户目标与学习计划；⑤ 最近行为 |
| **3. 输出** | 有序的「今日学习建议」列表，每条含：**动作类型 + 目标 + 可解释原因 + 依据数据** |
| **4. 需要多少数据** | **零**。前置关系是学科固有知识（人工/LLM 提议 + 人工确认），掌握度我们已有 |
| **5. 适合我们吗** | ✅ **完全适合**，且是本阶段唯一能真正落地的核心能力 |
| **6. 改造成本** | 中（新表 1 张 + 服务层 1 个 + API + 前端 1 处），无新框架、无新重型依赖 |
| **7. 可直接引入吗** | 没有现成可用的开源实现（PyEdmine 的 LPR 是研究代码），**需要自研**，但可以照搬 PyEdmine/MoocRadar 的**思路**而不是代码 |

## 3. Step 3：结合我们的真实情况

### 3.1 数据规模的冷酷现实

| 指标 | 当前生产值 | 深度 KT 的经验门槛 | 差距 |
|---|---|---|---|
| 用户数 | **1** | 10³~10⁴ | 10³ 倍 |
| 题目数 | **8** | 10³~10⁴ | 10³ 倍 |
| 作答记录 | **4** | 10⁵~10⁶ | **10⁵ 倍** |
| 知识点数 | **0** | 10²~10³ | — |
| 题目-知识点关联 | **0** | 需要全覆盖 | — |

> 数据来源：大阶段 2 部署后生产库实测（users 1 / questions 8 / answer_records 4 / wrong_book_items 2 / knowledge_points 0 / question_knowledge_points 0 / user_knowledge_point_mastery 0）。

**这张表决定了技术路线，而不是反过来。** 任何需要「从数据里学」的方法，在 5 个数量级的差距面前都是自欺欺人。

### 3.2 现有资产盘点（避免重复造轮子 —— 最重要的发现）

调研中发现：**本项目已经有一个相当完整的「计划 / 推荐 / 对话 / RAG」基础**，大阶段 3 大量工作应该是**改造与接线**，而不是新建。

### 3.3 三个关键缺口

#### 缺口 1（最重要）：`parent_id` 是「归属层级」，不是「前置依赖」

现有 `KnowledgePoint.parent_id` 表达的是**分类归属**（如「二叉树」属于「树」），语义是 *is-a / part-of*。而「树依赖链表」表达的是**学习顺序上的前置依赖**（prerequisite），语义是 *must-learn-before*。

二者**不能混用**：
- 把 `parent_id` 当前置用 → 语义错误，且会破坏现有管理后台的树形展示与删除约束（`ondelete=RESTRICT`）；
- 混在一张表里 → 无法表达「A 是 B 的父类但 B 不依赖 A」「C 依赖 A 和 B 两个前置」这类真实情况（树只有一个父节点，前置关系是多对多的 DAG）。

**结论：需要新增一张边表**（详见 §4.2）。这是本阶段**唯一需要动 Schema 的地方**。

#### 缺口 2：没有「今日学什么」的聚合输出

现有 `plans` 是**中长期计划**（按周/月，`scheduled_date` 粒度到天，但生成时是「一次性铺满整段时间」）。缺的是**每天开屏时的动态建议**：今天这 30~60 分钟到底干什么、按什么顺序、为什么。

#### 缺口 3：`generate_study_plan` 与掌握度完全脱钩

`study_planner.py` 的 prompt 只吃 `major/grade/goal/daily_minutes/weeks/subjects`，**没有 mastery、没有 wrong_book、没有前置关系**。所以现在的「个性化」其实是「按专业和目标的模板化」，而不是「按学习状态的个性化」。

### 3.4 三阶段路线（数据规模门禁驱动）

```
                    数据规模门禁
阶段            用户数      作答记录      技术路线
```

### 4.3 打分公式（确定性、可解释、可测试）

对**每个候选动作**计算 `score`，按分数降序取 Top-N（默认 3~5）。权重全部集中在 `services/recommendation.py` 的常量区（与 `mastery.py` 同一范式，**不散落 magic number**）。

候选动作有 4 种类型：

| 动作类型 | 触发条件 | 基础分 |
|---|---|---|
| `review_wrong` 复习错题 | 存在 `next_review_date <= today` 且未 mastered 的错题，且其关联 KP 命中候选集 | 最高 |
| `review_weak` 巩固薄弱知识点 | `mastery_score < WEAK_THRESHOLD(60)` 且有作答历史 | 高 |
| `learn_new` 学习新知识点 | 前置知识点全部满足「掌握度 ≥ READY_THRESHOLD」且自身无作答记录 | 中 |
| `practice` 加练 | 已学但 `attempt_count` 不足的 KP | 中低 |

打分因子（建议初值，全部可调、全部有测试）：

```
score = BASE[action]
      × urgency(review_item)        # 逾期天数越久越高，封顶
      × (1 + gap_weight × (100 - mastery_score)/100)   # 越弱越优先
      × difficulty_fit(profile, kp) # 与用户年级/画像的难度适配
      × goal_bonus(kp, goals)       # 命中用户目标/计划科目则加权
      × recent_recency_penalty      # 最近刚练过则降权（避免刷同一个点）
      × unlock_bonus(kp)            # 学会它能解锁的下游知识点数量越多越高
```

**`unlock_bonus` 是「学习顺序」的关键**：在 DAG 上计算「若掌握本 KP，有多少后置 KP 的前置条件被满足」，这是纯粹的图统计，天然可解释。

**reason 字段（回答「为什么推荐这个」）** 由公式的**分解项**自动生成，不是 LLM 编的：

```
"最近 3 次作答错了 2 次"                        ← 来自 wrong_book / answer_records
"掌握度 42%，低于薄弱线 60%"                    ← 来自 mastery
"它的前置「链表」掌握度 78%，已满足开始条件"      ← 来自前置 DAG 检查结果
"这是你学习计划《数据结构期末》中的知识点"        ← 来自 StudyPlan/PlanItem 命中
"学会它可以解锁 3 个后续知识点"                  ← 来自 unlock 图统计
```

> **硬约束**：reason 是**模板拼装**的结构化事实，LLM 只允许在此基础上做**润色表述**（V3），不允许生成新的数值或事实。

## 5. 推荐系统 V2 设计（本轮不实现，只定义门禁与路线）

### 5.1 V2-a：BKT 极简自研版（数据门槛低）

不引入 `pyBKT`，用闭式贝叶斯更新（几十行、纯函数）：

```
P(known) 先验 L0；学习率 T；猜测率 G；失误率 S
观察答对：P(L|correct) = P(L)(1-S) / [P(L)(1-S) + (1-P(L))G]
观察答错：P(L|wrong)   = P(L)S     / [P(L)S     + (1-P(L))(1-G)]
转移：    P(L') = P(L) + (1-P(L))T
```

- 参数来源：**全局默认值**（文献常见区间 L0≈0.3, T≈0.2, G≈0.2, S≈0.1），等单知识点作答 ≥ 30 次后允许 per-KP 微调。
- 与现有 mastery 的关系：**并存、可对比**，不直接替换。用 `MasteryOut` 增加一个 `bkt_probability` 字段做双轨观测，跑一段时间后再决定是否切换。
- 可测试性：闭式公式 → 单元测试可精确断言数值。

### 5.2 V2-b：pyBKT 参数拟合（数据门槛高）

- 触发条件：`单知识点作答中位数 ≥ 30` **且** `总作答 ≥ 5000`。
- 做法：离线脚本从 `answer_records` 导出长表 → `pyBKT` 拟合（服务器 Linux 走 C++ 后端）→ 参数落库 → 在线用闭式更新做推理。
- **不在请求路径上训练**（保证 API 延迟与稳定性）。

### 5.3 V2-c：深度 KT（DKT/SAKT/AKT）

- 触发条件：`总作答 ≥ 100,000` **且** `用户数 ≥ 1000`。
- 在此之前，**任何引入 torch 到后端运行时的行为都视为违规**。
- 参考实现：`pyKT`（benchmark）、`PyEdmine`（多任务）、`EduKTM`（模型动物园）。

### 9.5 风险

| # | 风险 | 等级 | 缓解 |
|---|---|---|---|
| 1 | **前置关系质量差 → 路径推荐错误** | 高 | LLM 只提议不落库；管理员确认；`source` 字段可追溯；可批量停用 |
| 2 | 成环导致路径遍历死循环/CDE | 高 | 写入前做可达性检查 + 遍历带 visited 集 + 单测覆盖成环拒绝 |
| 3 | 生产 `knowledge_points = 0`，功能**无数据可跑** | 高 | 前端做完整空态；提供管理员**批量导入知识点 + 前置关系**的最小入口；不自动造数据 |
| 4 | 打分权重「拍脑袋」导致建议不合理 | 中 | 权重集中 + 单测断言单调性；reason 展示打分依据，便于人工核对 |
| 5 | 建议与现有 `StudyPlan` 语义冲突（两套「今天干什么」） | 中 | 明确分层：`PlanItem` = 中长期计划，`today 建议` = 动态；建议只读，不自动改计划 |
| 6 | 新表引入 Schema 治理回归 | 中 | 沿用大阶段 2 已固化的 revision/freeze/drift 流程，不改基础设施 |
| 7 | 范围蔓延到 V2 深度学习 | 中 | 门禁常量 + 测试；未达标即拒绝 |
| 8 | 生产数据被污染（为了演示造数据） | 高 | **禁止**自动生成测试数据；所有测试走独立测试库 |

### 9.6 决策结果（已由用户确认，2026-10-01）

| # | 问题 | 决策 | 对设计的影响 |
|---|---|---|---|
| 1 | 前置关系的建模 | ✅ **新增 `knowledge_point_prerequisites` 边表** | 不动 `parent_id` 语义；本阶段唯一 Schema 变更；需新 Alembic revision `20261001_003` |
| 2 | 本轮范围 | ✅ **只做 V1** | 不做 V3（`ai_teacher.py` 不创建）；V2 仅固化门禁常量与测试 |
| 3 | 建议的落点 | ✅ **只读展示** | 「今日建议」不写入 `PlanItem`，避免与既有计划产生两套「今天干什么」；无新增写路径 |
| 4 | 复习排期 | ✅ **本轮不动，保持固定间隔** `{1:1,2:3,3:7,4:15,5:30}` | **不引入 `py-fsrs`**，不改复习语义，零回归面（`py-fsrs` 留待后续独立小阶段） |
